# UX レビューの手順と出力形式

LLM の UX レビューが失敗する型は決まっている: **一般論の羅列**、**根拠の無い断定**、**優先度の無い大量の指摘**、**見ていないものへの言及**。
この手順はそれぞれを潰すためにある。

## 1. 目標を確定する（評価を始める前に）

次の 4 つが分かるまで指摘を書かない。依頼から読み取れなければ推定し、推定だと明記する。

- 誰の画面か（初めての人 / 熟練者 / 管理者 / 外部の人）
- その人が達成したいこと（主要タスク 1〜3 個）
- プラットフォームと利用環境（PC / モバイル / 両方、片手・外出中か）
- レビューの目的（リリース前の確認か、改善の種探しか、2 案の比較か）

目標に触れない違反は、重大度が「軽微」を超えることはほぼ無い。

## 2. 証拠の種類ごとに、言えることを限定する

| 見ているもの | 言えること | 言えないこと（「未検証」へ送る） |
| --- | --- | --- |
| スクリーンショット・静止画 | 表示されている情報、文言、視覚的な優先度、ターゲットの見た目の大きさ、コントラスト（色値が分かるなら） | 操作後の反応、遷移、読み込み、エラー時の表示、キーボード操作、スクリーンリーダー |
| 動く画面（ブラウザで操作した） | 実際に辿った経路の反応・遷移・表示状態 | 辿っていない分岐、他の端末・回線、実ユーザーの頻度 |
| コード | 状態の分岐の有無、文言、入力の種類（`type` / `inputmode`）、セマンティクス、フォーカス管理、エラー時に入力が残るか | 描画結果の見え方、実際の読み込み時間 |
| 仕様書・PRD・フロー図 | 手順の数、聞いている情報、外れた道が定義されているか | 見た目、文言の実際（書かれていなければ） |
| ワイヤーフレーム | 構造、優先度、手順、状態の網羅 | 最終的な見た目・文言・性能 |
| 自動検査（axe、Lighthouse 等）の結果 | その検査のルールに違反しているか | タスクを達成できるか（自動検査はタスクのユーザビリティを証明しない） |

コードで状態の分岐を確かめる例: 空配列のときの描画、`catch` で何を表示するか、送信中にボタンが無効になるか、エラー後にフォームの値が残るか。

## 3. タスクを歩く

主要タスクごとに、開始地点から完了まで 1 手ずつ辿る。各手で次の 4 つの問いに答え、1 つでも No ならその手を問題の候補にする（cognitive walkthrough、Wharton ら 1994）:

1. ユーザーはこの手をやろうと思うか（目標とこの操作がつながっているか）
2. 操作できる場所に気づくか（見えているか、見つかるか）
3. それが目的の操作だと分かるか（ラベル・アイコンがユーザーの言葉か）
4. 操作したあと、前に進んだと分かるか（反応があるか、結果が見えるか）

あわせて、各手の interaction cost（読む量、入力の量、覚えておく必要、待ち）を書き留める。
最後に外れた道を歩く: 入力を誤る、途中でやめる、戻る、通信が切れる、データが 0 件 / 大量。

## 4. 観点を当てる

タスクを歩いて見つからなかったものを、観点で補う。**対象に関係する観点だけ**を当てる。

| 対象に含まれるもの | 当てる観点（reference） |
| --- | --- |
| フォーム・登録・購入・設定 | `task-efficiency.md` のフォームの節、`errors-feedback-states.md` の検証とエラー |
| 削除・送信・支払いなど取り返しのつかない操作 | `errors-feedback-states.md` の確認と Undo |
| 一覧・検索・ナビゲーション | `ia-navigation-mobile.md` |
| 非同期処理・待ち | `errors-feedback-states.md` の応答時間と読み込み表示 |
| モバイル | `ia-navigation-mobile.md` のモバイルの節 |
| 課金・サブスク・同意・通知の許可 | `accessibility-ethics.md` のダークパターンの節 |
| 文言が多い画面 | `ux-writing.md` |
| 全般 | `principles.md`（Nielsen 10 原則を最後の取りこぼし確認に使う） |

## 5. 候補を検証して統合する

最初に出た候補をそのまま返さない。各候補を次の順で通す:

1. **観察**: 何を見てそう判断したか（画面上の位置、コードの行、仕様の節）を書けるか。書けなければ捨てる。
2. **再現**: 同じ手順で同じことが起きるか。条件付き（「0 件のとき」）ならその条件を書く。
3. **意図の確認**: 意図的な設計・既知の慣習・製品の制約ではないか。そうなら却下するか、問いとして返す。
4. **統合**: 根本原因が同じ候補は 1 件にまとめ、症状が出る場所を列挙する（「保存ボタンの位置が画面ごとに違う」は 1 件）。
5. **費用対効果**: 直す費用が便益を明らかに上回るなら、却下するか「後回し」と明記する。

**却下した候補を 1〜5 件、理由つきで残す**（「好みの問題」「プラットフォームの慣習どおり」「別の指摘と同根」など）。抑制が効いていることを示すためで、水増しはしない。

## 6. 重大度を付ける

発見と重大度付けは分ける（発見しながら付けると不正確になる）。候補が出そろってから、次の問いを上から順に当て、最初に Yes になった段階を付ける:

| 問い | 重大度 |
| --- | --- |
| 主要タスクを完了できない、またはデータ・お金・作業を失う。欺いて、望まない契約・課金・個人データの提供をさせる | **4 致命的**（出す前に直す） |
| 完了はできるが、多くの人が迷う・誤る・大きく遠回りする。回復が難しい。法令・WCAG A/AA に反する。被害が小さく後から取り消せるダークパターン（配信同意の事前チェックなど） | **3 重大** |
| 一部の人・一部の条件で遠回りや小さな誤りが起きる。回復は容易 | **2 軽微** |
| 見た目・文言の整い。タスクへの影響はほぼ無い | **1 磨き込み** |

判断材料は 3 つ: **頻度**（どれくらいの人が遭遇するか）、**影響**（遭遇したら困る度合い）、**持続性**（一度覚えれば済むか、毎回困るか）。
共通部品の問題は全画面で繰り返すので一段上げてよい。到達経路の無い理論上の問題は 3 以上にしない。

## 7. 出力形式

```markdown
## 前提
- 対象: （見たもの。証拠の種類）
- 想定ユーザーと主要タスク: （推定なら「推定」）

## 判定: 直してから出す / 直したほうがよい / このままでよい
（1〜2 文の理由。主要タスクを検証していないなら「このままでよい」は出さない）

## 指摘（重大度順）
### 1. [重大度 3] （1 行で問題を書く）
- 誰が・どこで: （例: 初めて請求書を作る人が、手順 3 の顧客選択で）
- 何が起きる: （例: 新規顧客の作り方が見つからず、別画面へ戻る）
- 根拠: （画面の位置 / コードの箇所 / 原則名と出典）
- 直し方: 観察できる完了条件で書く（例: 「顧客選択の候補が 0 件のとき、その場で新規作成できる」）
- 確信度: 高 / 中 / 低（低なら確かめ方を書く）

## 良い点
（そのまま残すべき判断を 2〜5 件。直すときに壊さないため）

## 検討して却下した候補
- （候補）: （却下理由）

## 未検証
- （見ていない状態・端末・操作。確かめ方）
```

- 件数の上限: 簡易レビューは 5 件、詳細レビューは 12 件。超えた分は「その他（重大度 1〜2）」として 1 行ずつにまとめる。
- 直し方を「改善する」「分かりやすくする」と書かない。誰が見ても達成したか判定できる条件で書く。
- 総合点（「7/10」）は出さない。根拠を示せないため。
- 2 案の比較なら、指摘の列挙ではなく「主要タスクごとにどちらの負担が小さいか」の表で返す。
