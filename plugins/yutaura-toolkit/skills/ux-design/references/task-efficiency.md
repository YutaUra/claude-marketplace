# 目的達成までの負担を減らす

## interaction cost で比べる

ユーザーは「得られる便益 − かかる負担」が最も大きい行動を選ぶ。負担（interaction cost）は次の合計:
読む / スクロールする / 探す / 理解する / 正確に押す / 入力する / 覚えておく / 待つ / 注意を切り替える。

- 案を比べるときは、手順ごとにこれらを書き出して合計を比べる。**クリック数だけで比べない**。
- 負担の重さは人と環境で変わる: 読むことが重い人（ディスレクシア）、押すことが重い人（運動障害、揺れる電車）、待つことが重い環境（遅い回線）。
- 「離脱していない」は「負担が小さい」を意味しない。動機が強いユーザーは高い負担でも耐える（社内システム、行政手続き）。耐えている負担も負担として数える。

出典: https://www.nngroup.com/articles/interaction-cost-definition/ / https://www.nngroup.com/articles/3-click-rule/

### 3 クリックルールは使わない

3 クリックルールを支持する研究は無い。Porter（2003）では、3 クリックを超えても離脱は増えず、満足度も下がらなかった。
クリックの重さは均一ではない（ページ遷移とアコーディオンの開閉は別物）。読み込みの遅い 3 クリックは、速い 5 クリックより悪い。
3 クリックを守ろうとすると、トップに項目を並べすぎた「広く浅い」構造になり、探すコストが増える。

代わりに整えるもの:
- 各リンク・ボタンが行き先を予想させる言葉になっているか（情報の匂い）
- 現在地が分かるか（パンくず、選択状態、見出し）
- 主要タスクへの直接の入口があるか
- 読み込みが速いか

## 操作時間を KLM で見積もる

熟練者がミスなく定型操作を行う時間を、次の和で見積もる（Card, Moran, Newell）:

| 操作 | 記号 | 目安 |
| --- | --- | --- |
| キーを押す | K | 0.2 秒 |
| ポインタを合わせる | P | 1.1 秒 |
| キーボードとマウスの持ち替え | H | 0.4 秒 |
| 考える・決める | M | 1.35 秒 |
| システムの応答待ち | R | 実測 |

- 迷いが生じる箇所（選択肢を選ぶ、次に何をするか決める）に M を置くと、「手順は少ないが毎回考えさせる案」が遅いことが見える。
- 使えるのは熟練者の定型操作の比較まで。学習しやすさ・エラー・疲労・初心者は測れない。誤差は 2 割程度ある。

出典: https://en.wikipedia.org/wiki/Keystroke-level_model

## 聞かない・既定値を入れる・選ばせる

### 同じ情報を二度聞かない
- 同じ手続きの中で入力済みの情報は、自動で入れるか選べるようにする（「請求先は配送先と同じ」、前の手順の値を初期値に、エラー後も入力を残す）。
- WCAG 2.2 の 3.3.7（レベル A）の要件でもある。ブラウザの自動入力だけでは満たさない。例外はセキュリティ上必要な場合（パスワードの確認）と、情報がもう有効でない場合。

### 既定値を入れる
- 多くの人が選ぶ値を事前に入れる。既定値は「どう答えればよいか」の例も兼ねる。
- ユーザーは既定値を強く選ぶ（検索結果の 1 位は 2 位の 5 倍クリックされ、順位を入れ替えても 1 位が多く選ばれた）。だからこそ:
  - リストの先頭やアルファベット順の先頭のような、恣意的な既定値にしない
  - 売り手に有利なだけの選択肢（最も高いプラン、追加オプション）を既定にしない
  - プライバシー・マーケティング同意を事前にオンにしない（法規制の対象にもなりうる）

出典: https://www.nngroup.com/articles/the-power-of-defaults/ / https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html

### 想起より再認
- 最近使ったもの・履歴・候補・お気に入りを出す。アイコンにはラベルを付ける。
- 画面をまたいで比べさせない（比較ビュー、選択中の項目を残す）。
- 長い初回チュートリアルは覚えてもらえない。その場のヒントにする。

出典: https://www.nngroup.com/articles/recognition-and-recall/

## 見せる量を制御する

### 段階的開示（progressive disclosure）
- 最初はよく使う少数の機能だけを見せ、高度な機能・稀な機能は二次画面に回す（「詳細設定」）。
- 成功の条件は 2 つ:
  1. **分け方が正しい**: 二次画面に行くのが本当に稀であること。利用データかタスク分析で決める。よく使う機能を隠すと、毎回 1 手増える。
  2. **入口が分かる**: ラベルを見れば、その先に何があるか予想できること。
- 階層は 2 段まで。3 段以上が必要なら、機能そのものを整理する。

出典: https://www.nngroup.com/articles/progressive-disclosure/

### ウィザード（手順ごとの画面）か 1 画面か

| ウィザードが合う | 1 画面が合う |
| --- | --- |
| 初めての人・年に数回の作業（初期設定、申請） | 毎日使う人の定型作業 |
| 手順同士が独立している（前の手順に戻って比べる必要が無い） | 項目同士を見比べながら決める |
| 回答によって後の手順が分岐する | 全体を見渡したい・順不同で埋めたい |

ウィザードにするなら:
- 全体の手順と現在地を見せる
- 「次へ」ではなく次の手順の名前をボタンにする（「支払い方法へ」）
- 戻っても入力が消えない。途中で保存して再開できる
- 熟練者向けに速い経路を別に用意する

1 画面か 5 画面かの二択にしない。「比べる段階は 1 画面、住所と支払いの入力は別画面」のような分け方もある。

出典: https://www.nngroup.com/articles/wizards/

## フォームとチェックアウト

- **聞く項目を減らす**: 平均的なチェックアウトは 11.3 項目だが、ほとんどのサイトは 8 項目で足りる（Baymard）。削る候補: 氏名の分割（1 欄にする）、住所 2 行目（リンクで開く）、クーポン欄（折りたたむか自動適用）、請求先住所（「配送先と同じ」を既定に）。
  - 日本語の氏名は姓・名の分割やふりがなが業務上必要なことが多い。必要なら分け、不要なら 1 欄にする。必要かどうかを先に確かめる。
- **ゲスト購入を一番目立つ選択肢に**: 会員登録の強制だけを理由に 24% がカートを放棄した。ゲスト購入をテキストリンクにしたり下に置いたりすると、無いのと同じくらい悪い。アカウント作成は完了画面で、パスワード欄だけで提案する。
- **ラベルは入力欄の外、基本は上に**: 上揃えは視線が 1 回で済み、最も速い。プレースホルダーをラベル代わりにしない（入力すると消える、見直せない、既定値と誤認される、コントラストが低い）。
- **入力の検証は「離れたら検証、直したら即座に消す」**: 入力中に赤を出すとエラーが最も増え満足度も最低だった。欄を離れた時点で検証し、正しく直されたらその場で消す。桁数が決まっている欄（郵便番号）は規定の桁に達した時点で検証してよい。送信時の検証も省かない。
- **書式は受け入れて整える**: 電話番号のハイフン、全角・半角、前後の空白は受け入れて正規化する。書式の例を見せても 89% が違う形式で入力した。入力マスクは検証した地域・形式にだけ使い、手入力の逃げ道を残す。
- **住所は補完させる**: 郵便番号から住所を引く、入力中に候補を出す。候補が出ないときに手入力できる経路を必ず残す。
- **モバイルでは適切なキーボードを出す**: `type` / `inputmode` で数字・電話・メール用のキーボードにする（`ia-navigation-mobile.md`）。
- **任意項目と必須項目**: 数が少ない側に印を付ける。そもそも任意項目は本当に要るかを問う。

出典: https://baymard.com/blog/checkout-flow-average-form-fields / https://baymard.com/blog/make-guest-checkout-prominent / https://alistapart.com/article/inline-validation-in-web-forms/ / https://www.nngroup.com/articles/form-design-placeholders/ / https://baymard.com/blog/input-masking-form-field / https://baymard.com/blog/automatic-address-lookup

## オンボーディングと最初の価値

- 初回起動時の機能紹介カード・強制チュートリアルは原則置かない。タスク成績を改善しなかった（NN/g）。
- 順番は: まずオンボーディング無しでテストする → 困るなら UI を直す → それでも駄目なときだけ導入する。
- 初回に聞いてよいのは、使い始めるのに本当に必要な情報だけ。理由とスキップを付ける。見た目の設定は後回し。
- 価値を体験する前にログインや会員登録の壁を置かない。
- 説明は、その機能が使える場面になったら文脈の中で出す。

出典: https://www.nngroup.com/articles/mobile-app-onboarding/

### 空状態を最初の一手にする
空状態では 3 つを伝える: なぜ空か（まだ作っていない / 条件に合うものが無い / 権限が無い）、ここに何が入るか、最初の行動へのボタン（作成する、サンプルで試す、条件を外す）。
読み込み中に「データがありません」を出してから中身に差し替えるのは、信頼を失う最悪の形。

出典: https://www.nngroup.com/articles/empty-state-interface-design/

## 熟練者の手数を減らす

### 近道（アクセラレーター）
- 頻繁に繰り返す中核操作から、ショートカット・ジェスチャー・コマンドパレットを足す。メニューの横にショートカットを常時表示して覚えられるようにする。
- 近道でしかできない機能を作らない。ホバーでしか見つからない作りはタッチ端末に届かない。慣習的なショートカット（コピー、全選択、戻る）を上書きしない。

出典: https://www.nngroup.com/articles/ui-accelerators/

### 一括操作
- 一覧で繰り返す操作は一括にする: 全選択、選択中だけ出る操作バー（選んだもの全部に使える操作だけを並べる）、実行後の件数つきのフィードバック、取り消し。
- 一括の破壊的操作は、対象と件数を示して確かめる。

出典: https://www.nngroup.com/videos/bulk-actions-design-guidelines/ / https://www.nngroup.com/articles/data-tables/
