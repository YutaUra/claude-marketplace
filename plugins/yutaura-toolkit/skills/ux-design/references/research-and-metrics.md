# 調査・評価・指標

Claude にできるのは、目標の整理、仮説の明確化、机上の評価、テスト計画と指標の設計まで。**ユーザーが実際にどう振る舞うかは、Claude の推測では決まらない**。
設計やレビューの返答で「確かめ方」を書くときに、この reference から手法を選ぶ。

## 目標を言葉にする

### Jobs To Be Done（JTBD）
- 要件を「どの状況で、どんな進捗を得たいか」で書く。機能のリストはその後で導く。
- 形: 「〇〇のとき（状況）、△△したい（動機）。そうすれば □□ できる（得たい成果）」
- ジョブには機能面・感情面・社会面がある（「経費精算を早く終わらせたい」の裏に「上司に差し戻されたくない」）。
- 本人に「なぜ買ったか」を聞く手法ではない。決断に至った経緯と状況を集めて共通項を取り出す。

出典: https://www.christenseninstitute.org/theory/jobs-to-be-done/ / https://hbr.org/2016/09/know-your-customers-jobs-to-be-done

### タスク分析
- 目標を頂点に、タスク → サブタスクと分解する（階層的タスク分析）。目標は「サービスに登録する」、タスクは「フォームに入力する」。
- 各タスクについて、頻度、認知的な負担、順序、初心者と熟練者の違いを書く。頻度が高いタスクほど 1 手の削減が効く。

出典: https://www.nngroup.com/articles/task-analysis/

### ペルソナとジャーニーマップ
- ペルソナは調査に基づき、設計判断に効く情報だけで作る（趣味や凝ったキャッチコピーは削る）。調査なしの想像ペルソナはチームの思い込みを固定する。
- ジャーニーマップは 1 人の行為者 × 1 シナリオで書く。要素はシナリオと期待、段階、行動・思考・感情、改善の機会。仮説の部分は「仮説」と明記する。「マップは根拠以上に信頼できない」。
- 時間をかけて進む・チャネルをまたぐシナリオに向く。単一画面の改善ならユーザーフローや wireflow で足りる。

出典: https://www.nngroup.com/articles/persona/ / https://www.nngroup.com/articles/why-personas-fail/ / https://www.nngroup.com/articles/journey-mapping-101/

## 評価の手法

| 手法 | 向く問い | 規模の目安 | 限界 |
| --- | --- | --- | --- |
| **定性ユーザビリティテスト（思考発話）** | どこで迷い、なぜ迷うか | 1 回 5 人。直してまた 5 人、を繰り返す | 数値（時間・成功率）の比較には使えない |
| **定量ユーザビリティテスト** | 成功率・時間が基準を満たすか、案 A と B のどちらが良いか | 20 人以上 | 「なぜ」は分からない |
| **ヒューリスティック評価** | 原則に照らして問題になりそうな箇所 | 評価者 3〜5 人が独立に評価して統合 | ユーザーテストの代わりにはならない。原則違反が問題とは限らない |
| **cognitive walkthrough** | 初めての人が操作を学べるか | 1 タスクずつ | 定番のパターンに使うのはやりすぎ |
| **カードソート / ツリーテスト** | 分類とラベルがユーザーの考え方に合うか | カードソート 15 人以上、ツリーテストは定量なら 50 人程度 | ページの見た目や文脈は反映されない |
| **A/B テスト・行動ログ** | 実際の利用でどちらが良いか | 統計的に有意になる量 | 「なぜ」は分からない。短期指標に最適化しすぎる危険 |

### 5 人で十分の意味
- 似たユーザーが似た使い方をする場合、5 人で問題の約 85% が見つかる（1 人あたりの発見率の平均 31% から）。1 回 15 人より、5 人 × 3 回の反復のほうがよい。
- 利用者群が明確に分かれるなら群ごとに 3〜4 人。定量なら 20 人以上。

出典: https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/ / https://www.nngroup.com/articles/how-many-test-users/

### テストのタスク文の書き方
- 現実的な状況と目標を書き、UI のラベル名や手順を書かない（「40 ドル以下の靴を買ってください」。「『絞り込み』を押して…」とは書かない）。
- 意見ではなく行動を見る。参加者は自分を賢く見せようと発言を調整する。

出典: https://www.nngroup.com/articles/thinking-aloud-the-1-usability-tool/ / https://www.nngroup.com/articles/task-scenarios-usability-testing/

## 指標

| 指標 | 中身 | 注意 |
| --- | --- | --- |
| **タスク成功率** | 二値（成功 / 失敗）で取る | 部分成功を 0.5 のように数値化して平均しない。小さいサンプルでは信頼区間を付ける（Adjusted Wald） |
| **タスク時間** | 成功したタスクの所要時間 | 思考発話をさせると時間が汚れる |
| **エラー率** | タスク中の誤操作の数 | 何をエラーと数えるか事前に決める |
| **SUS** | 10 項目 × 5 段階、0〜100 点 | 平均 68。パーセントではない |
| **SEQ** | タスク直後に「この課題はどれくらい簡単だったか」を 7 段階で 1 問 | 平均 5.3〜5.6。5 未満なら理由を聞く |
| **HEART** | Happiness / Engagement / Adoption / Retention / Task success | 目的に合う次元だけ選び、目標 → 行動に表れるシグナル → 指標の順に定義する（Goals-Signals-Metrics） |

- 数値は単体では判断できない。比較対象（前のバージョン、競合、基準値）を決めてから測る。
- 満足度の自己申告と行動は一致しないことがある（失敗したのに「簡単だった」と答える人がいる）。

出典: https://www.nngroup.com/articles/success-rate-the-simplest-usability-metric/ / https://measuringu.com/sus/ / https://measuringu.com/seq10/ / https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/

## 優先度付け: Kano モデル

| 分類 | 意味 | 扱い |
| --- | --- | --- |
| 当たり前品質（Must-be） | 無いと不満、あっても満足は増えない | 欠けていたら最優先で直す |
| 一元的品質（One-dimensional） | 多いほど満足 | 競合と比べて投資を決める |
| 魅力品質（Attractive） | 無くても不満は無い、あると喜ばれる | ユーザーは口にしないのでインタビューでは出にくい |
| 無関心品質 | どちらでもよい | 作らない |
| 逆品質 | あると不満 | 作らない・外す |

- 分類は時間とともに「魅力 → 一元的 → 当たり前」と移る。
- 分類はアンケート（各機能について「ある場合」「ない場合」を 2 問聞く）で決め、チームの印象で決めない。

出典: https://en.wikipedia.org/wiki/Kano_model
