# エラー・フィードバック・状態

## エラーを分けて防ぐ

| 種類 | 何が起きているか | 起きやすい人 | 効く対策 |
| --- | --- | --- | --- |
| **スリップ** | 意図は正しいが操作を誤る（隣を押す、別の欄に入れる） | 慣れて「自動操縦」になった熟練者 | 制約、候補の提示、良い既定値、寛容な入力形式、似た操作を離す |
| **ミステイク** | 目標の立て方・仕組みの理解がずれている | 初めての人、メンタルモデルが違う人 | 慣習に合わせる、手がかりを明確にする、結果をプレビューする |

- 「ユーザーはいずれ仕組みを学ぶ」は誤解。消費者向けでは学ぶ前に去る。研修や注意書きを増やすのは対策にならない。
- 制約の例: 復路の日付に往路より前を選べない、数字以外は無視して区切りを自動で入れる、日時はプリセット（明日・1 時間後）を出す。
- 間違いの最中に控えめに知らせる: 文字数の残り、本文で「添付」と書いたのに添付が無い、など。ただし空欄のまま次の欄へ移っただけでエラーにしない。
- 影響が大きく確かめにくい操作は、適用前に結果を見せる（一括置換のプレビュー、送信前のプレビュー）。

出典: https://www.nngroup.com/articles/slips/ / https://www.nngroup.com/articles/user-mistakes/

## 確認ダイアログか Undo か

判断の順番:

1. **取り消せる操作か?** → 取り消せるなら **確認しない。すぐ実行して Undo を出す**。さらにゴミ箱などの二段目の復元手段を用意できるとよい。
   - 習慣化した「閉じる → OK」は一続きの動作になり、警告は読まれなくなる。「Undo のつもりで警告を使うな」（Raskin）。Apple HIG も、よく行う取り消し可能な操作には破壊的でもアラートを出さないよう求めている。
2. **取り消せない（送金、外部への送信、物理的な処理）かつ重大かつ稀か?** → 確認ダイアログを使う。
   - 対象を具体的に書く（ファイル名、件数、金額、宛先）
   - ボタンは結果を表す言葉にする（「3 件を削除」「削除しない」）。「はい / いいえ」「OK」にしない
   - 破壊的な選択肢を既定（Enter で押されるボタン）にしない
   - 日常的な確認はスキップできるようにする
3. **頻繁な操作に確認を出していないか?** → 出しているなら「オオカミ少年」になっている。確認を外して Undo に替える。
4. **最も危険で稀な操作（リポジトリの削除など）** だけ、名前の入力を求める。多用するとその入力も反射で行われる。

法的・金銭的な取引やユーザーデータの削除では、「取り消し」「入力のチェック」「送信前の確認」のどれかを必ず用意する（WCAG 2.2 の 3.3.4、AA）。

出典: https://alistapart.com/article/neveruseawarning/ / https://www.nngroup.com/articles/confirmation-dialog/ / https://developer.apple.com/design/human-interface-guidelines/alerts / https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html

## エラーメッセージ

- **何が起きたか**を平易に、正確に書く。「エラーが発生しました」で済ませない。
- **どう直すか**を示す。直し方が推測できるなら選ぶだけで済むようにする（「〒100-0001 は千代田区です。こちらに直しますか?」）。在庫切れなら再入荷時期や通知登録を示す。
- **責めない**。「無効」「不正」「誤り」のような落ち度を示す言葉を避ける。
- **発生源の隣**に、色だけに頼らず（アイコンと文言を添えて）出す。送信時にまとめて出すなら、画面上部に一覧と各欄へのリンクを置き、各欄の隣にも出す。
- **入力を消さない**。エラーになった欄だけを直させる（パスワードなど安全上の理由がある欄は除く）。
- **強さを影響に合わせる**: 軽微なものはインラインかバナー、対応必須の重大なものだけモーダル。エラーをトーストで出さない。
- エラーコードは、問い合わせや診断に必要なときだけ添える。

出典: https://www.nngroup.com/articles/error-message-guidelines/ / https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html

## 応答時間と待ちの見せ方

| 待ち時間 | ユーザーの感じ方 | 見せるもの |
| --- | --- | --- |
| 0.1 秒以内 | 即時 | 結果だけ。特別な表示は要らない |
| 1 秒以内 | 流れは途切れないが遅れに気づく | 何も出さないか、押した箇所の押下状態だけ（短すぎる点滅は煩わしい） |
| 1〜10 秒 | 注意がそれ始める | 部品単位ならスピナー＋理由（「コメントを読み込み中」）。画面全体ならスケルトン |
| 10 秒超 | 別のことを始める | 進捗率か「3 / 50 件」、残りの見込み（「約 3 分」と幅を持たせる）、中止ボタン。可能ならバックグラウンドに回して完了を通知する |

- 静的な「読み込み中…」は止まっても区別できないので使わない。
- スケルトンは性能改善の代わりにはならない。まず実際に速くする。
- 押したボタンはすぐ押下・処理中の状態にし、二重送信は UI で防ぐ（「二度押ししないでください」と書かない）。
- **楽観的 UI**（成功したものとして先に反映する）は、失敗が稀で取り消せる操作（いいね、並び替え、既読）に限る。失敗したら状態を戻し、何が起きたかと再試行の方法を伝える。黙って戻すのは最悪。決済・送信には使わない。

出典: https://www.nngroup.com/articles/response-times-3-important-limits/ / https://www.nngroup.com/articles/progress-indicators/ / https://www.nngroup.com/articles/skeleton-screens/

## 通知とトースト

- **トーストを既定の手段にしない**。結果が画面に見えるなら追加の通知は要らない（ボタンの表示を「保存しました」に変える、一覧に追加された行を示す）。
- エラーと重要な情報をトーストで出さない。約 5 秒で消えたエラーに気づかず待ち続けた人が観察されている。拡大表示・大画面では視界の外に出る。読み返せない。
- どうしても使うなら: 1 度に 1 つ、操作は 1 つまで、操作付きのものは自動で消さない。Undo を付けるなら同じ操作を本文側にも置く（自動で消える中の Undo はキーボード・スクリーンリーダーの利用者に押しにくい）。
- フォーカスが移らない状態変化は支援技術にも伝える: 件数や成功は `role="status"`、エラーは `role="alert"`（WCAG 4.1.3）。重要でないものに `alert` を付けない。
- プッシュ通知・メール:
  - 割り込ませるのは「ユーザーの対応が必要」なものだけ。受け身の情報はバッジやアプリ内の一覧にする
  - 同時に何件も送るなら 1 件にまとめる
  - 通知の許可は、価値を体験した後に、何が届くかを説明してから求める
  - 種類ごとにオフにできるようにする。「設定でオフにできるから送ってよい」は誤り（多くの人は設定を変えない）

出典: https://www.nngroup.com/articles/indicators-validations-notifications/ / https://primer.style/accessibility/patterns/accessible-notifications-and-messages/ / https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html / https://www.nngroup.com/articles/push-notification/

## 状態の一覧

データや外部とのやり取りがある画面は、次のうち起こりうるものを全部決める。決めていない状態は、実装者がその場で決めることになる。

| 状態 | 決めること |
| --- | --- |
| 理想（データが適量ある） | 通常の表示 |
| 初回の空 | なぜ空か、ここに何が入るか、最初の一手のボタン |
| 条件に合うものが無い（検索・絞り込み） | 条件を示す、外す・変える導線、近い結果 |
| 読み込み中 | 待ち時間に応じた表示（上の表）。読み込み中に「0 件」を出さない |
| 一部だけ取れた | 取れた部分は見せ、欠けた部分を明示し、再試行できるようにする |
| エラー | 何が起きたか、ユーザー側か相手側か、再試行・代替手段 |
| 権限なし | 理由と、誰に何を頼めば使えるか（「管理者に〇〇の権限を依頼してください」） |
| オフライン・通信断 | 「オフライン」と書くより「いま何ができるか」。最終更新時刻。接続が要る操作は戻るまで無効に。グレーは無効と誤解されるので状態表示に使わない |
| 大量（1,000 件、長い名前） | ページ分け・仮想スクロール・省略と全文の見せ方 |
| 時間切れ（セッション切れ） | 事前に警告し、簡単に延長できる。切れても入力を失わない（WCAG 2.2.1 は警告後 20 秒以上の猶予を求める） |

- 裏側の変化でユーザーに影響するもの（在庫切れ、価格の変更、他の人の編集）は、黙って反映せず、理由を添えて見せ、選ばせる。
- 起動時はアラートを出さず、キャッシュかプレースホルダーに控えめなラベルを添える。
