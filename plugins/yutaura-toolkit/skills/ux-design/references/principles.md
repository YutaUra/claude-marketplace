# UX の原則と法則（判断にどう使うか）

原則は判断の起点で、法則ではない。Nielsen の 10 原則は 249 件のユーザビリティ問題を因子分析して絞った経験則であり、Shneiderman 自身も黄金律は「出発点」だと書いている。
各項目は「設計時に何を問うか」の形で書く。

## Nielsen の 10 ユーザビリティヒューリスティクス

| # | 原則 | 設計・レビューで問うこと |
| --- | --- | --- |
| 1 | システム状態の可視化 | 操作のたびに反応があるか。いま何が起きていて、どこにいるか分かるか |
| 2 | 現実世界との一致 | ユーザーの言葉・順序・概念で書かれているか。社内用語やデータ構造が見えていないか |
| 3 | ユーザーの主導権と自由 | 間違えたときの非常口（戻る・取り消す・キャンセル）があるか |
| 4 | 一貫性と標準 | 同じものは同じ名前・同じ見た目・同じ位置か。プラットフォームの慣習に沿うか |
| 5 | エラーの防止 | 誤りが起きない作り（制約・既定値・候補）になっているか。危険な操作の前に確かめる機会があるか |
| 6 | 想起より再認 | 覚えさせずに見せているか（選択肢、履歴、前画面の情報） |
| 7 | 柔軟性と効率 | 熟練者の近道があるか。初心者には見えなくても困らないか |
| 8 | 美的でミニマルなデザイン | 目標に関係しない情報が、関係する情報と競っていないか（「フラットにせよ」ではない） |
| 9 | エラーの認識・診断・回復 | エラーが平易な言葉で、原因と直し方を示しているか |
| 10 | ヘルプとドキュメント | 必要な場面で、その場に、短く手順で示されているか |

出典: https://www.nngroup.com/articles/ten-usability-heuristics/

## Shneiderman の 8 つの黄金律（Nielsen と重ならない部分）

- **完結性のある対話**: 一連の操作には始まり・途中・終わりがあり、終わりを明示する（注文完了画面）。
- **フィードバックの大きさを操作の重さに合わせる**: 頻繁で小さな操作には控えめに、重大な操作には十分に。
- **主導権はユーザーに**: 熟練者は予期しない変化を嫌う。勝手に並び替わる・勝手に遷移する作りを避ける。

出典: https://www.cs.umd.edu/users/ben/goldenrules.html

## Norman の設計原則

- **シグニファイア**: 「押せる」ことを知らせる手がかり（境界・形・位置・慣習）を付ける。逆に、押せないものを押せそうに見せない（色付きの見出し、下線付きの静的テキスト）。
  - フラットにしすぎると手がかりが消える。矢印アイコンだけは最も弱い手がかり。
- **マッピング**: 操作部と結果の対応を空間的・概念的に自然にする（上のボタンが上のものを動かす）。
- **フィードバック**: 操作の結果をすぐ、操作した場所の近くに返す。
- **制約**: できない操作はそもそもできなくする（物理的・論理的・文化的な制約）。
- **概念モデル**: ユーザーが「これはこういう仕組みだ」と理解できる一貫した像を与える。
- **実行の淵と評価の淵**: 問題が「何をすればいいか分からない（実行）」のか「何が起きたか分からない（評価）」のかを分けて直す。評価の淵には「気づく」と「解釈する」の 2 段階があり、表示が見えていても意味を取り違えることがある。

出典: https://www.nngroup.com/articles/two-ux-gulfs-evaluation-execution/ / https://www.nngroup.com/articles/clickable-elements/

## Laws of UX（使いどころと限界）

| 法則 | 判断への使い方 | 限界・誤用 |
| --- | --- | --- |
| **Fitts の法則** | よく使う・重要なターゲットは大きく、近くに。送信ボタンは最後の入力欄の近く。隣との間隔を取る | 時間は距離に比例しない（対数）。画面端の利点はマウスのみで、タッチでは遅くなった例がある |
| **Hick の法則** | 素早く選ばせたい場面では選択肢を絞り、推奨を目立たせる | 絞りすぎると選択肢が抽象的になる。長いメニューも構造があれば使える |
| **Miller の法則（7±2）** | 画面をまたいで覚えさせる量を減らす根拠に使う | メニュー項目数の上限に使うのは誤用。作業記憶は約 4 チャンクという見解もある |
| **Jakob の法則** | ユーザーは他のサイトで覚えた動作を期待する。慣習に合わせる | 大きく変えるなら新旧を選べる移行期間を設ける |
| **Tesler の法則** | 削れない複雑さはシステムに引き受けさせる | 複雑さは消えず、置き場所が移るだけ |
| **Doherty の閾値** | 応答を 400ms 未満にすると作業の流れが保たれる | 遅延をわざと入れて「価値が高く見せる」手法は慎重に |
| **Postel の法則** | 入力には寛容に（全角・半角、ハイフン、前後の空白を受け入れて正規化） | 意味が曖昧な入力まで推測で受け入れることではない |
| **Peak-End の法則** | 体験は山場と終わりで記憶される。完了画面・エラー画面を丁寧に作る。否定的な山場（障害時の不親切なエラー）を潰す | 途中がどうでもよいわけではない |
| **Goal-Gradient 効果** | 複数手順のフローでは現在地と残りを見せる | 人での根拠は薄い。進捗の水増しは欺瞞になる |
| **Zeigarnik 効果** | 中断したタスクは覚えている。途中保存と再開の導線を用意する | 1920 年代の実験。「未完了」で煽る用途には使わない |
| **Von Restorff 効果** | 主要な操作だけを目立たせる | 目立たせるものが増えると互いに打ち消す。目立ちすぎると広告に見える |
| **系列位置効果** | 重要な項目は列の最初か最後に | UI 配置での検証は乏しい。テストで確かめる |
| **美的ユーザビリティ効果** | 見た目が良いと小さな問題は許される | 使いやすさの保証にはならない。テストでは行動を見る |
| **Pareto / Occam / Parkinson** | 利用の多いタスクを磨く。足すより削る。想定より短く終わらせる | どれも比喩・経験則で、数値として扱わない |
| **選択のパラドックス** | 選択肢過多は「起こりうるリスク」として扱う | メタ分析で平均効果はほぼゼロ。常に起きるわけではない |
| **認知負荷** | 目的に関係ない負荷（装飾、冗長なリンク、覚える必要）を削る | 目的そのものに必要な負荷は削れないし、削るべきでもない |

出典: https://lawsofux.com/ / https://www.nngroup.com/articles/fitts-law/ / https://www.nngroup.com/articles/minimize-cognitive-load/ / https://scheibehenne.com/ScheibehenneGreifenederTodd2010.pdf

## ゲシュタルト原則

- **近接**: 関係は余白で示す。見出しは自分の本文に近づけ、前の節から離す。ラベルは入力欄の近くに。
- **共通領域**: 枠で囲むと近接より強くまとまる。ただし枠を使いすぎるとノイズになる。全幅の色帯は「ページの終わり」に見えてスクロールを止める。
- **類同**: 見た目が同じなら同じ機能に見える。リンク色はクリックできるものだけに使う。役割の違うアイコンを似せない。
- レスポンシブで縦に積むと、横に並べて比べていたものが離れてグループが崩れる。幅ごとに確かめる。

出典: https://www.nngroup.com/articles/gestalt-proximity/ / https://www.nngroup.com/articles/common-region/ / https://www.nngroup.com/articles/gestalt-similarity/
