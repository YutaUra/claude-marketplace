# ux-design

UX の判断は、いつも同じ問いから始める: **誰が、どの状況で、何を達成したいのか。そこまでに何がユーザーの負担になっているか。**
画面の美しさや機能の数ではなく、目的を達成するまでの**負担の合計**と、**失敗したときに戻れるか**を扱う。

## この skill の前提（全モード共通）

1. **減らすのは「ステップ数」ではなく interaction cost**。読む・探す・理解する・正確に押す・入力する・覚える・待つ・注意を切り替える、の合計で案を比べる。
   - 「3 クリック以内」に根拠は無い（NN/g）。速い 5 クリックは、遅く迷う 3 クリックに勝つ。
   - チェックアウトの離脱に効くのはステップ数より「考えさせる入力欄の数」（Baymard）。
   - ステップを減らすために 1 画面へ詰め込むと、読む・探すコストが増える。両方を見積もる。
2. **削れない複雑さはシステム側に移す**（Tesler）。既知の情報を聞き直さない、良い既定値を入れる、正規化はシステムがやる。
3. **エラーはユーザーのせいではなく設計の問題**。まず起きない設計にし、起きたら原因と直し方をその場で示し、取り消せるようにする。
4. **慣習に合わせる**（Jakob's Law）。独自の操作は、既存の型より明らかに優れているときだけ採る。
5. **原則は判断の起点で、チェックリストではない**。原則に反していても、その文脈で害が無ければ問題ではない。逆に原則を満たしていても、目標に届かなければ問題がある。
6. **Claude は実ユーザーではない**。机上の評価で言えるのは「問題になりそうな箇所」までで、問題の頻度・深刻さの最終判断はユーザーの行動データかユーザビリティテストで決まる。確かめていないことは「未検証」と書く。

## A. 設計モードの手順

### 1. 目標とタスクを確定する

依頼文・会話・リポジトリ（既存画面、用語、データモデル）を読み、次を書き出す:

- **誰が**: 利用者の種類（初めての人か、毎日使う熟練者か、両方か）。利用環境（PC / モバイル / 外出中 / 片手）。
- **どの状況で、何を達成したいか**（ジョブ）: 「〇〇のとき、△△したい。そうすれば□□できる」の形で 1〜3 個。機能名（「検索機能」）ではなく進捗（「先週の請求書を 10 秒で見つけたい」）で書く。
- **成功の判定**: 何が起きたら目標達成か。どれくらいの頻度で行うタスクか。
- **制約**: 法的に必要な確認、取り消せない処理（送金・外部送信）、既存の慣習。

不明点が設計を大きく左右するなら質問は 1 つまでにする。答えが無くても最も可能性の高い前提で進め、置いた前提を返答に書く。

### 2. 理想の流れ（ハッピーパス）を書き、負担を見積もる

- 目標達成までの手順を、**ユーザーの行動**（読む・選ぶ・入力する・待つ）の列で書く。画面の列ではない。
- 各手順について「なぜこれをユーザーがやる必要があるのか」を問う。答えが「システムの都合」なら削るかシステム側へ移す。
- 案が複数あるときは interaction cost で比べる。定型操作の速さを比べたいなら KLM で秒数を見積もる（`task-efficiency.md`）。

### 3. 負担を削る（効く順）

1. **聞かない**: 既に知っている情報、推測できる情報、後で聞けば足りる情報を聞かない（アカウント作成は購入後に回す、など）。
2. **既定値を入れる**: 多くの人が選ぶ値を事前に入れる。ただし売り手に有利なだけの既定値やプライバシーに関わる事前オンは避ける。
3. **選ばせる**: 想起ではなく再認。最近使ったもの、候補、履歴を出す。
4. **見せる量を絞る**: よく使うものだけ最初に見せ、残りは段階的に開示する（2 階層まで）。
5. **熟練者の近道を足す**: ショートカット・一括操作は「追加の経路」として。近道でしかできない機能は作らない。

### 4. 外れた道を設計する

ハッピーパスだけの設計は未完成。少なくとも次を決める（`errors-feedback-states.md`）:

- 入力の誤り（いつ検証するか、どこに何を出すか、入力を残すか）
- 取り消し（Undo で足りるか、確認が要るか。確認は「重大・稀・取り消せない」ときだけ）
- 待ち（何秒かかりうるか、何を見せるか、中断できるか）
- 空・読み込み中・エラー・部分的なデータ・権限なし・オフライン・時間切れのうち、この画面で起こりうるもの
- 途中離脱と再開（入力途中で閉じたらどうなるか）

### 5. 文言を決める

ボタンは「動詞＋対象」、エラーは「何が起きたか＋どう直すか」、空状態は「なぜ空か＋最初の一手」。専門用語・社内用語を使わない（`ux-writing.md`）。

### 6. 誰も取り残していないか・欺いていないかを確かめる

- アクセシビリティ: 色だけに頼らない、タッチターゲット、二度入力させない、認証で記憶や転記を強いない（`accessibility-ethics.md`）。
- 倫理: 解約は登録と同じ経路・同じ手間でできるか。断る選択肢に罪悪感を与える文言を付けていないか。偽の緊急性・事前チェック・隠れコストが無いか。

### 7. 返す

返答に含めるもの:

1. 目標（ジョブ）と成功の判定、置いた前提
2. フロー（ハッピーパス＋外れた道）。手順の列か、場所・操作・遷移を書いた breadboard の形で
3. 主要な判断とその理由（「確認ダイアログではなく Undo にした。削除は頻繁で、ゴミ箱から 30 日戻せるため」）。却下した代替案も 1 行ずつ
4. 状態ごとの振る舞いと文言の案
5. 検証が必要な仮説と、その確かめ方（「初回の人が〇〇に気づくかは 5 人の操作テストで確かめる」）

画面の配置まで描く必要があるなら、ここで決めたフローと状態を入力として **wireframe skill** を使う。

## B. レビューモードの手順

**`references/review-protocol.md` を必ず読んでから始める**。要点:

1. **目標を先に確定する**: 誰が何を達成する画面かが分からないまま評価を始めない。分からなければ推定して明記する。
2. **証拠の種類を確かめる**: スクリーンショット・動く画面・コード・仕様書・ワイヤーのどれを見ているかで、言えることが違う。見ていないものは「未検証」に送る。
3. **タスクを歩く**: 主要タスクを 1 手ずつ辿り、各手で 4 つの問いを当てる（cognitive walkthrough）: その操作をしようと思うか / 操作できる場所に気づくか / それが目的の操作だと分かるか / 操作後に進んだと分かるか。
4. **観点を当てる**: 関係する reference の観点だけを当てる。全原則を総当たりで採点しない。
5. **候補を検証して統合する**: 再現できない候補は捨てる。根本原因が同じものは 1 件にまとめる。好みだけの指摘、意図された慣習、費用が便益を上回るものは却下する。
6. **重大度順に、件数上限つきで返す**: 上位 5 件（簡易）〜 12 件（詳細）まで。各件に「誰が・どの手順で・何に困るか」「根拠」「観察できる完了条件の形の直し方」を付ける。良い点と、検討して却下した候補も書く。最後に判定を 1 つだけ出す。

## よくある俗説（設計でもレビューでも根拠にしない）

| 俗説 | 実際 | 代わりに見るもの |
| --- | --- | --- |
| 3 クリック以内に届かせる | 支持する研究が無い。3 クリックを超えても離脱も満足度も悪化しなかった（Porter 2003） | 各ステップの手がかりの強さ、現在地、待ち時間 |
| メニューは 7±2 項目まで | 7±2 は作業記憶の話。メニューは見て選ぶ（再認）ので当てはまらない | 画面をまたいで覚えさせていないか |
| ステップが少ないほど速い | KLM では操作数の多いショートカット案のほうが速い例がある | interaction cost の合計 |
| 選択肢は少ないほど売れる | メタ分析（Scheibehenne 2010）で平均効果はほぼゼロ。条件次第 | 比較しやすさ、推奨の明示 |
| 確認ダイアログを増やせば安全 | 頻発すると読まずに押され、効かなくなる | Undo、制約、プレビュー |
| チュートリアルを入れれば分かる | カード形式のチュートリアルはタスク成績を改善しなかった（NN/g） | UI 自体の修正、文脈内のヒント、空状態 |
| 成功はトーストで知らせる | 結果が画面に見えれば追加の通知は不要。トーストは見落としとアクセシビリティの問題が多い | 結果そのものの表示、インラインの状態変化 |
| きれいなら使いやすい | 使いやすく「感じる」だけ（美的ユーザビリティ効果）。テストで問題を見落とす原因になる | 行動（成功率・時間・エラー） |
| プレースホルダーでラベルを省くとすっきり | 入力すると消え、見直せず、既定値と誤認される | 入力欄の外の常時表示ラベル |
| 「75% の人が親指で操作する」 | 出典不明。持ち方は数秒ごとに変わる（Hoober） | 主要操作の大きさと、片手でも届くか |

## やらないこと

- 原則やヒューリスティクスを総当たりで採点し、「10 点中 7 点」のような根拠の無い総合点を出す
- 目標に関係しない一般論（「一貫性を保ちましょう」）を指摘として並べる
- 見ていない画面状態・操作感・アニメーションについて断定する
- 実ユーザーのデータの代わりに、自分の感想を「ユーザーはこう感じる」と書く
- 依頼に無い機能を「UX 向上のため」として足す（足すなら提案として分け、負担が増えないことを示す）
- ダークパターンを「コンバージョン改善策」として提案する
