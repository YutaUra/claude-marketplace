# eval-driven-tuning

LLM の振る舞いは、読んだ感想では改善できない。**失敗を名前で特定し、その失敗を確実に起こすケースで、直す前と直した後を同じ条件で比べる**。比べた結果は、件数に見合った強さでしか主張しない。

## この skill の前提

1. **観察から始める**。「良くなりそう」な変更から始めない。直す対象は、実際に起きた（または起こせた）失敗モード。
2. **baseline が落ちないケースからは何も学べない**。両方が通るケースは、差を測る道具として壊れている。
3. **採点器も成果物と同じだけ疑う**。悪い出力を通す採点器は、無いより悪い。採点の中身は実行役に見せない。
4. **1 回の実行は 1 標本**。同じ依頼・同じ版でも結果は揺れる。試行は最低 3 回、比べる単位はケース。
5. **少数ケースで言えることは少ない**。5 ケース以下では統計的に何も確定しない。それでも測るのは、回帰・識別力のなさ・副作用が見つかるから。言えないことは「言えない」と書く。
6. **直すのは最も低い層から**。必ず守らせたいことは prompt ではなく runtime（hook・権限・道具の有無）で強制する。prompt の文言は最後の手段。
7. **Claude の採点は Claude の判断**。外部の目が無い限り、judge と実行役は同じ系統の偏りを共有する。伏せ比較・二値判定・コード判定・ユーザーの抜き取り確認で補い、残る制約は報告に書く。

## 規模を決める

始める前に、ユーザーに規模と件数を示す（実行回数はケース数 × 試行回数 × 2 条件で増える）。

| 規模 | 使う場面 | ケース | 試行 |
| --- | --- | --- | --- |
| 軽量 | 1 つの失敗モードを直す（「最終報告だけ英語になる」等） | 狙ったケース 2〜3 ＋ 引っかけ 1〜2 ＋ held-out 1〜2 | 各 3 |
| 標準 | skill / agent を全体的に改善する、新しく作った skill の効果を確かめる | 失敗モードごとに 1〜2 ＋ 引っかけ ＋ held-out 2〜3（計 6〜15） | 各 3（重要なものは 5） |

改善のラウンド数の上限（既定 5）も最初に決める。

## 手順

### 1. 目的と失敗を確定する

- 何を改善したいのか、測った結果で何を決めるのか（採用するか・どちらの案にするか）を 1 文で書く。
- 実際の失敗の事例（会話ログ・出力・ユーザーの不満）を集める。手元に無ければ、現行版を代表的な依頼で数回走らせる。
- 求めていない振る舞いなら、eval を作る前に指示を足すだけでよいことがある（「そもそも頼んでいない」失敗に採点器は要らない）。

### 2. エラー分析で失敗モードに名前をつける → `references/error-analysis.md`

生の transcript を読み、1 件ずつ 4 値でトリアージする（成果物の失敗 / ケースの問題 / 実行環境の問題 / 期待値の誤り）。成果物の失敗だけを、**最初に誤った地点**で分類する。サイレント失敗（中身が抜けている・やっていない作業の完了報告など）のチェックリストを毎回当てる。

### 3. テストケースを作る → `references/test-cases.md`

- 狙った失敗を起こす `target`、直しすぎると落ちる `trap`、以前から通る `regression`、改善中は見ない `heldout` を用意する。
- **禁止ルールを足すなら、やりすぎを検出するケースを必ず組にする**。
- レビュー・検出系は、答え（仕込む欠陥と、指摘されてはいけない箇所）を先に書いてから題材を作る。素のモデルが元から見つけられるものだけを仕込むと差が出ない。
- 依頼文・fixture・コミットメッセージに答えが漏れていないか、作った後に読み直す。
- 短い eval で再現できない条件（長時間セッションの終盤など）は、再現を試み、できなければ「未検証」と記録する。

### 4. 採点器を作る → `references/graders.md`

- コードで判定できることはコードで。解釈が要る部分だけ二値の judge（採点役サブエージェント）。
- assertion は 1 つに 1 事実、成果物から観察できる形、互いに従属しない形で書く。
- 使う前に、既知の良い出力と悪い出力で 1 回ずつ確かめる。
- 少数でもユーザーが判定したケースを用意し、judge との不一致を 1 件ずつ読む。

### 5. 走らせて、伏せて採点する → `references/running.md`

- baseline は変更前の版（新規なら「なし」）。同じ依頼・同じ fixture・同じタイミングで、試行ごとに新しいコンテキストとコピーを使う。
- 実行役に assertion や改善の狙いを渡さない。baseline がインストール済みの同名 skill を読み込んでいないか transcript で確かめる。
- 完了通知の tokens・時間はすぐ `meta.json` に保存する。
- 伏せて採点する:

```bash
KIT=<この skill のディレクトリ>/scripts/eval-kit.ts
bun "$KIT" blind   <work>/runs <work>/blind                       # 採点役には blind/ だけを見せる
bun "$KIT" unblind <work>/grades.jsonl <work>/runs/blind-key.json > <work>/results.jsonl
bun "$KIT" compare <work>/results.jsonl
```

- 実行の途中で成果物や採点を直さない。

### 6. 分析する → `references/analysis.md`

- 主指標はケース単位の勝ち・負け・引き分け。合計の通過率より先に見る。
- **採用ルール**: 以前通っていた assertion を 1 件も落としていない、dev と held-out の差がどちらも 0 以上でどちらかが正、trap で新たに落ちたものが無い、副作用が改善に見合う。
- 識別力のない assertion・揺れている assertion・欠測の偏りを確かめる。
- 長さ・tokens・時間・起動数の副作用を並べる。

### 7. 直して、記録する → `references/changes.md`

- 層を診断する（ハーネス → モデル → 知識 → prompt → テスト自体）。
- 失敗のクラスを起こさない原則を 1 文で書き、1 回に 1 つだけ変える。同じ失敗に 2 回効かなければ、文言をいじらず層の診断に戻る。
- 採点を変えたら、変更前の採点でも測る。テストを弱めて通すのは改善ではない。
- 手順 5〜6 に戻る。予算に達したか、採用ルールを満たしたら、held-out を 1 回だけ回して終える。
- `evals/evals.json` にケースと `note`（識別力・漏洩・再現性の知見）を残し、コミットメッセージに方法・数字・副作用・測っていないことを書く。

## 報告の型

ユーザーへの最終報告には次を含める:

1. 狙った失敗モードと、選んだ層・変更（1 つずつ）
2. 評価の方法: ケース数（種類別）・試行回数・伏せ方・採点の方法（コード / judge / ユーザー）
3. 結果: ケース単位の勝ち負け、回帰の有無、held-out の結果、主要な数字（「13/13 は変わらず、誤検知 1 → 0、severity の不一致 7 → 3」）
4. 副作用: 長さ・tokens・時間・起動数
5. 言えないこと: 件数による限界、識別力のなかったケース、再現できなかった条件、judge と実行役が同じ系統であること、修正後に再採点していない部分
6. 採否の判断と、次に測るべきこと

## やらないこと

- 読んだ印象だけで「改善した」と言う。改善したと言うのは、測ったときだけ
- 結果を見てから採点基準を緩める。改善中に held-out を見る
- 失敗したやりとりを prompt にそのまま貼る。テストのケースを見分ける記述を成果物に入れる
- 候補で落ちるケースを外す。欠測の試行を黙って除く
- 5 ケース以下の結果を「有意」「効果なし」と言い切る
- ALWAYS / NEVER を積み重ねて直す。理由を説明する形にするか、runtime で強制する
- 評価の作業ファイルを成果物のディレクトリ（リポジトリ）に置く
