# 変更と記録: 正しい層で、1 つずつ、クラスで直す

## 1. どの層で直すか（低い層を先に検討する）

失敗の原因になりうる層は 5 つある。**prompt は最後の手段**。

| 層 | 例 | 直し方 |
| --- | --- | --- |
| ハーネス | ツール・権限・hook・どのタイミングで何がコンテキストに入るか | 道具を外す、hook で強制する、注入の位置を変える |
| モデル | 能力の限界 | モデルを変える、タスクを分割する。直せないなら対象外にする |
| 知識 | skill の reference・docs・例 | 欠けている知識を足す、古い記述を直す |
| prompt | 指示の文言・構成・例 | 文言を変える |
| テスト自体 | ケース・assertion の誤り | ケースを直す（ただし §5 を守る） |

### 必ず守らせたいことは、prompt ではなく runtime で強制する

prompt に書いた制約は、長い作業や自己改善の過程で「簡略化のため」に落とされる。警告を書き足しても回避率は下がらなかった（self-improvement-loops の STOP の事例）。

- 「ツール X を使うな」なら、ツール X を設定から外す（permissions）。
- 「commit の前に必ず Y」なら、PreToolUse hook でブロックして Y を促す（このリポジトリの `check-comments.sh`・`pnpm-best-practices-gate.sh`）。
- 「毎回この言語で」のように、prompt の先頭にあるだけでは効かない指示は、hook で**直近に**入れ直す（`reply-language-context.sh`）。

### 指示の位置と、名指しの範囲

このリポジトリの言語 hook の調整で分かったこと:

- **位置**: 指示がプロンプトの先頭にあるだけだと、直前に続く大量の英語のツール出力の方が強く効く。必要な指示は、判断の直前に置く。
- **言語**: 英語のツール出力の直後に英語の指示文を置くと、返答直前の文脈が英語一色になる。指示文自体を目的の言語で書く。
- **名指しの範囲**: 指示が「短い進捗メモ」を名指ししていたため、最終報告は対象外と解釈された。適用してほしい場面は、取りこぼしやすいもの（最終報告・表のある長いまとめ）を明示的に名指しする。
- **重複**: 同じ指示が同じ位置に二重に入っていた（Code Mode の REPL と Poll の両方で発火）。重複は効きを強めず、コンテキストを汚すだけ。

### 事後に直す仕組みより、予防を先に試す

出てしまった失敗を書き直させる仕組み（Stop hook で書き直しを命じる等）は、出力のコストが二重にかかる。予防策の効果を測ってから検討する。

## 2. クラスで直す（その 1 件に当てたパッチにしない）

- 失敗したやりとりを prompt に貼らない。その失敗の**クラス**を起こさない原則を 1 文で書く。原則が書けないなら、まだ診断が終わっていない（`error-analysis.md` に戻る）。
- ケースの言い回しだけを変えて走らせ、直ったことを確かめる。1 つの言い回しでしか通らない修正は、その言い回しへのパッチにすぎない。
- テストのケースを見分ける記述（ケース固有の名前・キーワード・答え）を成果物に入れない。それは過学習。「テストに無い同じ種類の依頼でも効くか」を自問する。

## 3. 1 回に 1 つ変える

- 複数を同時に変えると、言えるのは「束としての効果」だけで、どれが効いたかは分からない。後から部品ごとの効果を推測しない。
- 一括の書き直しをしない。蓄積した文脈を LLM に丸ごと書き直させたら、18,282 tokens が 122 tokens に縮み、精度は何も適応させない状態より下がった（ACE の事例）。変更は項目単位の差分にする。
- 前のラウンドで却下した案を繰り返さない。却下理由と一緒に記録し、次は構造的に違う案を試す。

## 4. 文言の作法

- 大文字の ALWAYS / NEVER / MUST を足したくなったら黄色信号。理由を説明する形に直す（なぜそうすべきかが分かると、モデルは規則に書かれていない場面にも広げられる）。窮屈な MUST の積み重ねは、別の場面での振る舞いを壊す。
- 例（few-shot）は 0 件から測り、eval で見えた失敗のクラスにだけ足す。足すなら易しい例・境界の例・してはいけない例の順で 3〜5 件。
- 役割の記述（「あなたは熟練の〜」）は 1 行にとどめる。言葉は出力の形と、判断の基準に使う。
- 「最後までやり切れ」系の指示を足すときは、同じ強さの検証の指示と組にする。検証なしの粘り強さは、完了に見せかける方向に働く。

## 5. 改善の証拠にならないもの

- **同じ作業で変えた採点**: 成果物と一緒に assertion を変えたなら、変更前の assertion でも測る。
- **弱めたテスト**: 基準を緩めて通った、ユーザー役の依頼を唯一通る道に誘導した、今の挙動に合わせて状況を書き換えた — どれも何もテストしていない。テストを直してよいのは、テスト側が誤っている証拠があるときだけ。
- **自分で書いたテストだけで通った**: 改善の作業中に作ったケースは、作業者の想定に偏る。held-out で確かめる。

## 6. 変更の前に書く仮説（コミットメッセージにも流用する）

```
観察: <どのケースのどの試行で何が起きたか（記録の場所）>
仮説: <最初に誤った地点と、そのメカニズム>
変更: <どの層の、何を、1 つだけ>
期待: <どの assertion が動くか。動かないはずのケースはどれか>
リスク: <やりすぎると何が落ちるか（対応する trap ケース）>
```

測れない変更は「未検証」と明記し、改善と呼ばない。

## 7. 刈り込み

追加を重ねたら、効いていない記述を 1 つずつ外して測る（leave-one-out）。品質が同じなら短い方を採る。複数のケースで実行役が同じ補助手順を自前で書いていたら、skill に script として同梱する合図。

## 8. 記録する

### evals.json

- ケースと assertion は skill のディレクトリの `evals/evals.json` に残す（`test-cases.md` §10）。
- 測定から分かったこと（識別力が無かった、答えが漏れていた、再現できなかった、assertion が従属していた）は `note` に書く。

### コミットメッセージ（Why を書く）

既存のコミット（webapp-review・ux-design）と同じ形で、次を含める:

- 何が問題だったか（観察した失敗）と、なぜこの層・この方法で直したか
- 評価の方法（ケース数・試行回数・伏せ方）
- 結果を数字で（「正解との severity 不一致: 7 件 → 3 件（2 試行合計）」「検出数 13/13 は変わらず」）
- 副作用（長さ・起動数・コスト）
- 測っていないこと（「修正後の再採点はしていない」「長時間セッションの条件は再現できていない」）

却下した案も、理由と一緒に短く残すと、同じ案を再発見しなくて済む。
