# 分析: 少数ケースで言えることと言えないことを分ける

## 1. eval-kit.ts compare の読み方

```bash
bun <skill のディレクトリ>/scripts/eval-kit.ts compare results.jsonl [--baseline NAME] [--candidate NAME] [--json]
```

入力は 1 行 1 assertion の JSONL（`unblind` の出力、または自分で書いたもの）:

```json
{"config":"baseline","case":"signup-form","trial":1,"assertion":"a1","passed":true,"split":"dev","tokens":12000,"duration_ms":60000}
```

| 出力 | 意味 | 見方 |
| --- | --- | --- |
| 判定と exit code | 0 改善・回帰なし / 2 決着つかず / 3 入力エラー / 4 回帰あり | 0 でも「採用してよい」ではない。§3 の採用ルールと副作用を見てから決める |
| ケース単位の勝ち・負け・引き分け | 各ケースの通過率（試行平均）を条件間で比べた結果 | **主指標**。合計の通過率より先に見る |
| 符号検定の p | 勝ち負けの偏りが偶然で起きる確率 | §2 の表と合わせて読む |
| 回帰した assertion | baseline で過半数通っていたのに候補で過半数落ちたもの | 1 件でもあれば採用しない（§3） |
| 識別力のない assertion | 両条件とも全試行で通過（または失敗） | 差の判断材料にならない。ケースを難しくするか外す（`test-cases.md`） |
| 揺れている assertion | 同じ条件で結果が割れる | 区間の幅を見る。3 回中 2 回なら 95% 区間は 21〜94% |
| 副作用 | tokens・時間の平均比 | §5 |
| 警告 | 欠測・試行不足・試行数の不一致 | 欠測が片方に偏っていたら比較をやり直す |

## 2. 少数ケースで言える範囲

### 試行はケースの中で平均し、ケースを単位に比べる

同じケースの試行どうしは似た結果になる。5 試行 × 4 ケースを「20 件」と数えると、確かさを大きく見積もりすぎる。比べる単位はケース。

### 勝ち負けの件数と、偶然では説明しにくい差（両側 p < 0.05）

引き分けを除いた勝ち負けの件数ごとに、偶然では説明しにくいと言える最小の結果（`scripts/lib/stats.ts` の `signTest` で計算）:

| 勝ち負けの件数 | 必要な結果 |
| --- | --- |
| 3〜5 | どの結果でも届かない（5 勝 0 敗でも p=0.063） |
| 6 | 6 勝 0 敗 |
| 7 | 7 勝 0 敗 |
| 8 | 8 勝 0 敗 |
| 9 | 8 勝 1 敗 |
| 10 | 9 勝 1 敗 |
| 12 | 10 勝 2 敗 |
| 15 | 12 勝 3 敗 |

ここから言えること:

- **5 ケース以下の評価は、統計的には何も確定しない**。それでも測る価値はある（明らかな回帰・識別力のない assertion・副作用が見つかる）が、結論は「この題材では差が出た / 出なかった」までにする。
- 「有意差なし」を「効果なし」と書かない。件数が少ないと、本当に差が無いときと、差を検出できないときで同じ結果になる。代わりに「この件数では、ケースの大半が入れ替わるほどの大きな差しか検出できない」と書く。

### 1 つのケースの安定性

| 結果 | 95% 区間（Wilson） |
| --- | --- |
| 3/3 | 44%〜100% |
| 5/5 | 57%〜100% |
| 2/3 | 21%〜94% |

3 回全部通っても、本当の成功率が半分程度である可能性は消えない。**毎回効いてほしい成果物**（hook・rules・skill の発火）は、k 回すべて通る率（pass^k）で見る。1 回あたり 75% の成功率なら 3 回連続で通るのは 42%。「ときどき効く」は「効く」ではない。

## 3. 採用ルール

次のすべてを満たしたときだけ候補を採用する:

1. **以前通っていた assertion を 1 件も落としていない**（`compare` の回帰リストが空）。合計が上がっていても、どこかを犠牲にした候補は採らない。
2. dev（狙ったケース）の差 ≥ 0、held-out の差 ≥ 0、かつどちらかが > 0。
3. trap（やりすぎ検出）のケースで新たに落ちたものが無い。
4. 副作用（§5）が、得た改善に見合う。

理屈が通っていることは採用の理由にならない。採否は測定で決める。

## 4. 結論を歪める典型

| 典型 | 何が起きるか | 対策 |
| --- | --- | --- |
| **勝者の呪い** | 同じケースで複数案を比べて最高だった案のスコアは、偶然の上振れを含む | 選ぶのに使っていない held-out の結果を報告する |
| **探索の分母を書かない** | 10 案試せば、効果が無くても 1 案くらいは偶然良く見える | 何案試したかを記録し、数値に「探索」「確認」のラベルを付ける |
| **黙った欠測** | 失敗した試行を除いて平均すると、残ったのは無作為な標本ではない | 欠測の件数を条件ごとに数える。偏っていたらやり直す |
| **消えたケース** | 候補で落ちるケースを外すのは、最も安い偽の修正 | `compare` はケースの欠落を回帰として扱う |
| **1 ケースへの依存** | 平均の差が 1 ケースの大差で決まっている | 1 ケースずつ外して結論が変わらないか見る |
| **採点器の誤差を無視** | judge が k 件誤判定するなら、k ケース分の差は採点の誤差かもしれない | `graders.md` §6 の不一致件数を結論に添える |
| **違反 0 件を 0% と書く** | 15 試行で違反 0 件でも、本当の率が 0 とは限らない | 「n 試行で 0 件。率の上限はおよそ 3/n」（rule of three）と書く |

## 5. 副作用を並べる

改善は必ず何かと引き換えになる。最低限これを並べて報告する:

- 出力の長さ（webapp-review の調整では、レポートが 1.4〜2 倍に伸びた）
- tokens・所要時間（`compare` の比）
- 起動するサブエージェントやツール呼び出しの数（6 本 → 8 本）
- 成果物（prompt・SKILL.md）自体の長さ。長さは bundle size のように追跡し、通過率を保ったまま減らす方向を目指す

品質が同じなら単純な方を採る。

## 6. 結論の書き方

| データ | 書き方 |
| --- | --- |
| 勝ち負けが §2 の表に届いた | 「n ケース中 w 勝 l 敗。偶然では説明しにくい差」 |
| 届かないが一方的 | 「n ケース中 w 勝 l 敗。この件数では確定できないが、同じ向きの差が続いた」 |
| 区別できない | 「差は区別できない」。「やや優位」とは書かない |
| 識別力が無かった | 「このケースは両方とも通り、差を測れなかった」。効果なしとは書かない |
| 直した後に測っていない | 「修正後の再採点はしていない」と明記する |
