# テストケース: 失敗を確実に起こし、差を見分けられるケースを作る

良いケースの条件は 1 つ: **baseline（現行版）が実際に落ち、正しく直した版なら通る**。両方とも通るケースからは何も学べない。

## 1. 何件作るか（個人規模の目安）

| 目的 | 件数 | 試行 |
| --- | --- | --- |
| 1 つの失敗モードを直す（軽量） | 狙ったケース 2〜3 ＋ 引っかけ 1〜2 ＋ held-out 1〜2 | 各 3 回 |
| skill / agent を全体的に改善する（標準） | 失敗モードごとに 1〜2 ＋ 引っかけ ＋ held-out 2〜3（計 6〜15） | 各 3 回（重要ケースは 5 回） |
| skill の発火（description）を調整する | 発火すべき 8〜10 ＋ 発火すべきでない near-miss 8〜10 | 各 3 回 |

件数が少ないことは恥ではないが、**言える範囲が狭くなる**ことは報告で必ず書く（`analysis.md`）。

## 2. ケースの種類（evals.json の `kind`）

| kind | 中身 | 集計 |
| --- | --- | --- |
| `target` | 狙った失敗モードを起こすケース | 改善の主指標 |
| `trap` | 引っかけ・near-miss。直しすぎると落ちるケース | 回帰チェック。1 件でも新たに落ちたら採用しない |
| `regression` | 以前から通っている代表的な依頼 | 回帰チェック |
| `adversarial` | わざと崩しにくる入力（red team） | 平均に混ぜない。「違反が 1 件でもあったか」で見る |

### 禁止ルールには必ず「やりすぎ」のケースを組にする

「範囲外の依頼は断る」を足すなら「挨拶まで断ると落ちる」ケースを作る。「severity を下げすぎるな」を足すなら「本当に Low のものを High にすると落ちる」ケースを作る。片方だけだと、振り子の反対側に倒れたことに気づけない（webapp-review の調整では、severity ルールを入れた結果 High を Medium に下げすぎた）。

## 3. 仕込んだ欠陥と引っかけ（レビュー系・検出系の成果物）

レビューや検出をする成果物は、**正解を構成から作る**と採点が厳密になる。

1. 先に答え（仕込む欠陥の一覧と、指摘されてはいけない箇所の一覧）を書く。
2. それに合わせて入力（diff・仕様・画面）を作る。
3. 欠陥ごとに assertion を 1 つ（「X を指摘している」）、引っかけごとに assertion を 1 つ（「Y を問題として挙げていない」）。

例: 脆弱性 13 件と、正しい実装なのに脆弱に見える引っかけ 3 件を仕込んだ diff。検出数・誤検知・severity の不一致を別々に数える。

**モデルが元から知っている範囲だけを仕込むと差が出ない**（webapp-review の評価では検出数は新旧とも 13/13 だった）。差が出るのは、成果物が足した知識や判断基準に依存する欠陥。仕込む前に「素のモデルがこれを見落とすか」を考え、見落としそうなものを入れる。

## 4. 合成ケースの作り方（次元 → タプル → 依頼文）

1. 失敗しそうな軸（次元）を 3 つ程度に絞る。例: 依頼の曖昧さ（明確 / 曖昧）、作業の長さ（短い / 長い）、ツール出力の言語（日本語 / 英語）。
2. 次元の値の組（タプル）を列挙し、失敗しそうな組を優先して選ぶ。
3. タプルを自然な依頼文に変える。**タプル作りと文章化は別の手順にする**（一度にやると言い回しが単調になる）。
4. 不自然なもの・意図とずれたもの・互いに似すぎたものを捨てる。

依頼文の現実味の確認: 「このユーザー（yutaura）が実際にこう書くか？」。教科書的な質問、丁寧すぎる仕様書のような依頼は不合格。実際の依頼は口語・省略・前提の書き漏らしを含む。

合成を使わない方がよい場面: 現実味を判断できる人がいない、実際の事例が十分ある、法務・医療など専門性が高い。

## 5. 答えを漏らさない（このリポジトリで実際に起きた失敗）

- **依頼文が答えを示唆する**: 「あとこれは細かいんだけど」と書いたため、どれが軽微な修正か自明になり、skill あり / なしで差が出なかった。判断させたいことを依頼文に書かない。
- **fixture が手順を書いている**: リポジトリ内の docs に「develop を取り込んでから再生成すること」と書いてあり、両方が正解した。fixture の文書・コミットメッセージ・ファイル名に答えが無いか、作った後で読み直す。
- **難しさが足りない**: ずれが 1 コミット・fast-forward・コンフリクトなしだと、git log を一度見れば分かる。現実の事故の条件（複数コミット・別の作業で注意が逸れている）まで寄せないと識別できない。

## 6. 再現できない条件は「未検証」として扱う

短い eval は新しいコンテキストで小さな題材を渡すので、**長時間セッションの終盤**・**大量のツール出力の後**・**注意が別の作業に向いている状態**を再現できない。言語の流れや、終盤の確認漏れはこの種類。

- 再現を試みる方法: 依頼の前に長い作業（英語のログを大量に読む等）を挟むケースを作る、実際の長いセッションのログから「最初に誤った時点の直前」までを再生する。
- それでも再現できなければ、その原則は「未検証のまま含めている」と evals.json の `note` とコミットに書く。再現できない eval で「同着だったので効果なし」と結論しない。

## 7. held-out を分ける

- 改善の作業中に一度も見ないケースを 1〜3 件残す（`split: "heldout"`）。
- held-out は改善が終わった最後に 1 回だけ回す。結果を見てから直したら、それはもう held-out ではない（次の改善では新しい held-out を作る）。
- dev の結果が悪いからといって dev のケースを差し替えない（形を変えた held-out の消費になる）。

## 8. fixture の作法

- 架空の固有名・ID・パスを具体的に書き込む。「ある同僚」「適当なファイル」のままだと毎回違う物が作られ、再現しない。
- ケース側に、成果物が派生させたテキスト（前の版が出力したレポートなど）を保存しない。改善中の部品の古い出力を正解として固定してしまう。
- ケースは 1 つの失敗モードを狙う。1 つのケースで多くを測ろうとすると、落ちたときに何が原因か分からない。

## 9. adversarial ケース（red team）

- 書くのは成果物の作者以外（別のサブエージェント）。作者は自分が強いと知っている所ばかり突く。
- 同じ手口の言い換え 10 個より、違う系統の手口 1 個ずつ 10 個の方が多くを学べる。
- 禁止結果は観測できる事象で書く（「危険な振る舞い」ではなく「確認なしに `rm -rf` を実行する」）。
- 「問題を解かずに完了したように見せる最も安い方法は何か」を別のサブエージェントに考えさせ、その抜け道を塞ぐケースを足す。既に塞いだものしか出なくなったら止める。

## 10. evals.json の形式

既存の skill（`ux-design` / `wireframe` / `project-manager-mode`）と同じ形式に、任意の欄を足す。

```json
{
  "skill_name": "<対象>",
  "evals": [
    {
      "id": 0,
      "name": "kebab-case の短い名前",
      "kind": "target | trap | regression | adversarial",
      "split": "dev | heldout",
      "prompt": "ユーザーの依頼文（実際の口調で）",
      "files": ["fixture のパス"],
      "expected_output": "期待する振る舞いの要約（採点役向けの説明）",
      "assertions": ["観察できる事実で書いた合否基準（graders.md）"],
      "note": "識別力が無かった・答えが漏れていた・再現できなかった等の、測定についての知見"
    }
  ]
}
```

`note` は捨てずに残す。次に同じ成果物を改善する人（未来の自分）が同じ罠を踏まないための記録になる。
