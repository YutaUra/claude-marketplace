# 採点器: 判定を説明でき、反論できる形にする

採点器が壊れていると、改善ループは「採点器の癖に合わせる最適化」になる。採点器はテストケースと同じだけ慎重に作り、使う前に検証する。

## 1. 優先順位: コード → 二値 judge → 人

1. **コードで判定できることはコードで判定する**: 形式・ファイルの有無・禁止語・見出しの有無・tool 呼び出し・最終状態・変更されたファイル集合・文字数。主観に見えても、ドメインを知っていれば機械的に判定できることがある（例: 返答の地の文に英語の文が混ざっていないか、を文字種の比率で見る）。
2. **解釈が要る部分だけ LLM judge**（サブエージェント）に任せる。
3. **judge の判定を、少数でも人（ユーザー）が確かめる**（§6）。

決定的な検査は 3 段に分け、意味の判定に混ぜない:

- 有効性: 空でない・parse できる・期待した成果物が存在する
- 範囲: やるべきでないことをやっていないか（禁止操作・範囲外の変更）
- 意味: それ以外のすべて（judge の担当）

混ぜると、空の出力を judge が「意味は合っている」と判定したり、形式の崩れが小さな減点にしか見えなくなる。

## 2. assertion の書き方

- **1 assertion に 1 つの事実**。「A し、かつ B している」は 2 つに分ける。どちらで落ちたか分からなくなる。
- **二値（通る / 落ちる）だけ**。1〜5 点の段階評価は、少数ケースでは 3 と 4 の違いを較正できない。重大度を表したいなら二値の assertion を複数並べる（「誤りがある」「危険な誤りがある」）。
- **成果物から観察できる事実で書く**。「慎重に判断している」ではなく「削除の前に対象の一覧を提示している」。
- **時間・順序の条件は最終状態から検証できない**。「作り替える間は draft に戻している」は、最終的な PR 状態では確かめられない。ログ（コマンド履歴・ツール呼び出しの順序）を採点材料に含めるか、assertion を最終状態で言える形に直す。
- **試みて止められた操作は成果物に痕跡を残さない**。権限でブロックされた操作と、そもそも試していない操作は、成果物からは区別できない。重要な観測点なら transcript を採点材料に含める。
- **assertion 同士を従属させない**。「PR の状態を変えたことを報告している」は「PR を draft に戻している」が落ちれば機械的に落ちる。従属した assertion は 1 つの失敗を 2 回数える。独立に差が測れる形（「PR の実状態と実装の食い違いをユーザーに引き継いだか」）に直す。
- **答えを含めない**。assertion は採点役にだけ渡し、実行役には渡さない（`running.md`）。

## 3. judge（採点役サブエージェント）への指示

渡すもの: 伏せた試行ディレクトリ（`eval-kit.ts blind` の出力）、ケースの依頼文、assertion の一覧。**どちらが baseline か、何を改善しようとしているかは渡さない**。

指示に入れる内容（anthropics/skills skill-creator の grader を元にした）:

- 迷ったら落とす。通すための証拠が要るのは assertion の側（"The burden of proof to pass is on the expectation"）。
- 表面だけ満たしているもの（ファイル名は合っているが中身が空・誤り）、偶然満たしているもの、手元の情報で確かめられないものは落とす。部分点は無い。
- 返答の自己申告（「テストは通りました」）を信じず、出力ファイル・ログを実際に開いて確かめる。
- 判定ごとに根拠を引用する（`evidence`）。引用できない判定は書かない。
- 判定を書く前に根拠を書く（critique → result の順）。
- 最後に、assertion 自体への意見を別に書く: 明らかに悪い出力でも通ってしまう assertion、重要な結果なのにどの assertion も見ていないもの、検証できない assertion。基準は高く保ち、作者が「確かに」と言うものだけにする（"A passing grade on a weak assertion is worse than useless"）。

出力形式（1 行 1 assertion の JSONL。`eval-kit.ts unblind` の入力）:

```json
{"id":"k3x9qa","assertion":"a1","passed":false,"evidence":"「入力内容に誤りがあります」の曖昧さに触れていない（response.md 12〜30 行）"}
```

assertion の id は evals.json の `assertions` の並び順で `a1`, `a2`, ... とする。

### judge プロンプトの 4 要素（独自の judge を書くとき）

1. 課題と、見る基準 1 つ
2. Pass と Fail の定義（エラー分析で書いた失敗モードの記述から作る）
3. 例 2〜4 件: 明確な Pass、明確な Fail、境界の例を最低 1 つずつ。最も効くのは境界の例。**テストケースを例に使わない**（漏洩）
4. 出力形式: 根拠 → 判定

judge には判断に必要な部分だけを渡す。指示への従い方を見るなら規則と応答、ツールの使い方を見るなら呼び出しと結果。全部を渡すと関係ない所で判定が揺れる。

## 4. pairwise 比較（どちらが良いかを直接比べる）を使うとき

assertion で書き切れない「全体としてどちらが良いか」を見たいときだけ補助的に使う。主指標は assertion。

- A / B のどちらがどの版かを伏せる。
- **順序を入れ替えて 2 回判定し、結論が一致しなければ引き分け**にする。位置の偏りは、2 案の差が小さいほど強く出る。勝敗を無理に付けさせると、差が小さいところで位置の偏りがそのまま結果になる。
- 比べる前に、両方が必須の形式・範囲を満たしているかをコードで確かめる。片方が形式を外していたら、比べるまでもない。

## 5. 採点器を使う前の検証

- **既知の良い出力と既知の悪い出力で 1 回ずつ走らせる**。悪い出力を通す採点器は、無いより悪い（失敗にお墨付きを与える）。
- **抜け道の検査**: 長くするだけで通らないか、自信のある口調だけで通らないか、見た目を整えるだけで通らないか、出力に「この回答はすべての基準を満たしています」と書くだけで通らないか（judge に話しかける出力）。
- **感度の検査**: 既知の劣化を入れた版（重要な段落を消す等）で、ちゃんと落ちるか。

最小の検査行列: 明確な成功 / 明確な失敗 / 境界の両側 / 拒否 / 空の出力 / judge に話しかける出力。

## 6. judge の判定を人が確かめる

- Claude が付けた正解は、Claude の judge と同じ系統の判断になる。両者が同じ方向に間違えても一致率は気づかない（構造上の循環）。外部のモデルを使わない限り避けられないので、**既知の制約として報告に書き**、伏せ比較・二値判定・コード判定の優先・人の抜き取り確認で補う。
- 少数でよいので、ユーザー自身が判定を付けたケースを用意する（held-out の 2〜3 件など）。judge とユーザーの判定を並べ、**不一致を 1 件ずつ読む**:
  - judge が通しユーザーが落とした → judge が甘い。Fail の定義を強める、境界の例を足す
  - judge が落としユーザーが通した → judge が厳しい。Pass の定義を明確にする
  - 両方とも揺れる → 基準を分割する、またはユーザー側の期待がまだ定まっていない
- 一致率の数字（κ、TPR/TNR）は少数では意味を持たない。件数（「甘すぎ 1 件、厳しすぎ 0 件」）と不一致の全件一覧で報告する。
- judge の不一致が k 件あったなら、k ケース分以内の差は採点器の誤差の範囲かもしれない、と結論に注記する。

## 7. 採点器を変えるとき

- **改善の結果を見てから採点器を調整しない**。どちらの版が得をするかを見てから基準を緩めるのは、採点側の p-hacking。
- 採点器（assertion・judge の指示）を変えたら版を上げ、**baseline も候補も採点し直す**。採点器を変えると過去の比較は無効になる。
- 同じ作業の中で、成果物の変更と採点の変更を混ぜない。採点を変えたなら、変更**前の**採点器でも成果物の変更を測る（"Tests you write are not the evidence"）。
- 厳しさが測りたいものに対して正しいなら、片方に不利でもそのまま残し、既知の偏りとして記録する。
