# comment-cleanup

Claude はコードを書くとき、コメントを過剰に書く癖がある。この skill は commit / push 前に diff を見直し、**残す価値のないコメントだけ**を削除する。

## 対象範囲

デフォルトの対象は「今から commit / push しようとしている変更で **追加された** コメント」:

- commit 前: `git diff --cached`（staged がなければ `git diff`）
- push 前: `git diff @{u}...HEAD`（upstream がなければ `git diff origin/HEAD...HEAD`）

既存コード由来のコメント（diff に含まれない行）は触らない。ユーザーが「ファイル全体」「リポジトリ全体」と明示した場合のみ範囲を広げる。

## 削除するコメント（デフォルトで削除）

| 種類 | 例 | なぜ削除するか |
| --- | --- | --- |
| コードの動作をなぞるだけ | `// ユーザーを取得する` の直後に `getUser()` | コード自体が語っている。乖離リスクだけが残る |
| セクション見出し・進行ナレーション | `// Step 1: バリデーション`, `// メイン処理` | 関数分割で表現すべき内容 |
| 変更説明（レビュアー向け） | `// タイムアウトを30秒に変更`, `// 以前は X だったが修正` | commit ログに書くべき内容。マージ後はノイズ |
| 自明な型・引数の説明 | `// name: ユーザー名` | シグネチャと名前で伝わる |
| 消したコードの残骸 | コメントアウトされた旧実装 | git 履歴にある |
| AI の自己言及 | `// テストを通すために追加`, `// 念のため` | 読み手に何も伝えない |
| 冗長な JSDoc/docstring | private 関数への「〜を行う関数です」だけの docstring | 情報量ゼロ |

## 残すコメント（削除禁止）

| 種類 | 例 |
| --- | --- |
| **Why not**（別の方法を選ばなかった理由） | `// new Date(dateStr) を使わない理由: ブラウザ間で解釈が異なるため` |
| 制約・不変条件（コードから読み取れないもの） | `// この順序は決済 API の仕様上変更不可` |
| 外部仕様・バグへの参照 | `// https://github.com/foo/bar/issues/123 のワークアラウンド` |
| ツール向けディレクティブ | `eslint-disable`, `@ts-expect-error`, `# type: ignore`, `# noqa`, `biome-ignore` |
| ライセンスヘッダ・著作権表記 | ファイル先頭の license comment |
| 公開 API のドキュメントコメント | export された関数・型の JSDoc / docstring / rustdoc（実質的な情報があるもの） |
| チケット付き TODO / FIXME | `// TODO(#456): リトライ処理を追加` |
| 意図的に非自明なコードへの警告 | `// パフォーマンスのため意図的に unrolled` |

判断に迷ったら基準は1つ: **「このコメントを消したとき、将来の読み手が誤った変更をするリスクが上がるか？」** 上がるなら残す。上がらないなら消す。

## 残すコメントも短くする

残す価値があるコメントでも、Claude は全部を説明しようとして長文化しがち。**削除ではなく圧縮の対象**として、以下の観点で書き直す:

- 読み手の判断を変える核心（制約・理由・参照先）だけ残し、背景説明・言い換え・結論の繰り返しは削る
- 目安は 1〜3 行。それを超えるなら「本当に全部ないと誤った変更をするか？」を問い直す
- コードから読み取れる部分の再説明が混ざっていたら、その部分だけ削る

```typescript
// Bad: 価値はあるが冗長（背景・経緯・言い換えが混ざっている）
// この関数では new Date(dateStr) を使っていません。なぜかというと、
// 入力データにはゼロパディングなしの日付（例: "2023-1-5"）が含まれることがあり、
// Date コンストラクタにそのような文字列を渡すとブラウザによって解釈が異なるためです。
// つまり Safari と Chrome で異なる結果になる可能性があります。
// そのため手動でパースする方式を採用しました。

// Good: 核心だけを短文で
// new Date() はゼロパディングなし日付("2023-1-5")の解釈がブラウザ依存のため手動パース
```

## 手順

1. 対象の diff を取得する（範囲は上記「対象範囲」に従う）
2. diff 中の追加コメント行を列挙し、上記の基準で削除 / 残置を判定する。残すものは冗長なら短文に書き直す
3. Edit で削除する。コメント行削除で不自然な空行が残る場合は空行も詰める
4. コメントだけでなく、削除により意味が変わらないことを確認する（文字列リテラル内の `//` や `#`、shebang を誤って消していないか）
5. staged だった変更なら `git add` し直す
6. 結果を報告する: 削除した件数・短縮した件数と、**残したコメントとその理由**（1行ずつ）

## 注意

- Markdown の `#` は見出しでありコメントではない。`.md` / `.mdx` は対象外
- YAML / TOML / .env のコメントは設定の説明として価値が高いことが多い。慎重に判定する
- テストコードの Arrange / Act / Assert コメントは、ユーザーの TDD ガイドラインで推奨されている構造化コメントなので残す
- 削除するか本当に迷うもの（境界例）は削除せず、報告に「要判断」として列挙する
