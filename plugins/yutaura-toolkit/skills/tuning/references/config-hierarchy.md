# 設定ファイルの階層と使い分け

## 階層構造

```
優先度（高い方が優先）:
1. Managed Policy（組織管理）      ← 変更不可
2. プロジェクトレベル設定           ← tuning で管理（デフォルトの変更先）
3. ユーザーレベル設定              ← tuning で管理（明示指示があるときだけ）
```

プロジェクトレベルの方がユーザーレベルより優先される。つまりプロジェクトに書けば
ユーザーレベルの設定を上書きできるが、逆はできない。これもデフォルトを
プロジェクトスコープに置く理由の一つ。

## 各設定ファイルの役割

### CLAUDE.md

**役割**: プロジェクトやユーザーの方針・規約・技術スタックを宣言する。

| スコープ | パス | 用途 |
|---|---|---|
| プロジェクト（デフォルト） | `<project>/CLAUDE.md` | プロジェクトの方針 |
| サブディレクトリ | `<project>/src/CLAUDE.md` | ディレクトリ固有の補足 |
| ユーザー | `~/.claude/CLAUDE.md` | 明示指示があった全プロジェクト共通の方針 |

**適している内容**:
- 技術スタックの宣言（言語、フレームワーク、パッケージマネージャー）
- コーディング規約（命名規則、ファイル構成）
- ワークフロー方針（コミット規約、ブランチ戦略）
- プロジェクト固有の制約や背景情報

**適していない内容**:
- 特定ファイルタイプに限定されるルール → rules/ を使う
- 複数ステップの手順 → skills/ を使う
- 一時的なタスク指示

### Rules（.claude/rules/*.md）

**役割**: 特定の条件下で適用される具体的なルールを定義する。

| スコープ | パス |
|---|---|
| プロジェクト（デフォルト） | `<project>/.claude/rules/*.md` |
| ユーザー | `~/.claude/rules/*.md` |

**適している内容**:
- ファイルタイプ別のルール（`paths: "**/*.ts"` で TS ファイルにのみ適用）
- 具体的な Do/Don't（コード例付き）
- フレームワーク固有のパターン
- セキュリティ・品質に関する制約

**適していない内容**:
- プロジェクト全体の方針 → CLAUDE.md を使う
- 手順書 → skills/ を使う

**サイズガイドライン**:
- 理想: 100行未満
- 許容: 100-500行
- 500行超: 分割を検討

**フォーマット**: `claude-code-rules` スキルの references/rule-format.md を参照。

### Skills（.claude/skills/*/SKILL.md）

**役割**: 再利用可能なワークフロー・手順を定義する。

| スコープ | パス |
|---|---|
| プロジェクト（デフォルト） | `<project>/.claude/skills/*/SKILL.md` |
| ユーザー | `~/.claude/skills/*/SKILL.md` |

**適している内容**:
- 複数ステップのワークフロー
- 外部ツールとの連携手順
- ドメイン固有の専門知識
- 再利用可能なスクリプトやテンプレート

**適していない内容**:
- 単純なルール → rules/ を使う
- プロジェクトの方針宣言 → CLAUDE.md を使う

## 決定フローチャート

```
フィードバックを受けた
│
├─ 特定のファイルタイプや状況に限定される？
│   ├─ Yes → rules/ に追加
│   └─ No ↓
│
├─ 複数ステップの手順やワークフロー？
│   ├─ Yes → skills/ に追加
│   └─ No ↓
│
└─ 方針・規約の宣言
    └─ CLAUDE.md に追加
```

「どのファイル種別か」を決めたら、次の「スコープの判断」でどの階層に置くかを決める。

## スコープの判断

**デフォルトはプロジェクトレベル**（`<project>/CLAUDE.md`, `<project>/.claude/`）。

```
ユーザーレベル（~/.claude/）に置くのは次のときだけ:
│
├─ ユーザーが「全プロジェクトで」「常に」「グローバルに」と明示した
│   例: コミットメッセージは常に日本語で書く
│
└─ 現在のリポジトリと無関係な、作業スタイル全般の方針
    例: 検索は grep ではなく rg を使う

上記に当てはまらない → プロジェクトレベル
    例: このプロジェクトでは pnpm を使う、API のベース URL
```

迷ったらプロジェクトレベルを選ぶ。後からユーザーレベルへ昇格させる方が、
広すぎるスコープを後から絞って各プロジェクトの挙動を壊すより安全。

なお `~/.claude/rules/` が nix 管理の symlink になっている環境では、
ユーザーレベルのルールはそもそも直接編集できない。この場合はプロジェクトレベルに
書くか、nix 側の設定変更手順を案内する。

## アンチパターン

### 設定の重複
同じルールが CLAUDE.md と rules/ の両方に書かれている。
→ 一箇所にまとめ、もう一方は削除する。

### スコープの不一致
プロジェクト固有の設定がユーザーレベルに置かれている。
→ プロジェクトレベルに移動する。

### 巨大な CLAUDE.md
CLAUDE.md が肥大化して読みづらい。
→ 具体的なルールは rules/ に、手順は skills/ に分離する。

### ルールの矛盾
異なるファイルで矛盾するルールが定義されている。
→ 優先度を明確にするか、統合する。

### 過剰な規定
些細なことまでルール化して設定が膨大になっている。
→ Claude がデフォルトで適切に判断できることはルール化しない。
