# 調査の切り分け手順

PM モードで調査を采配していると、「プロダクトの不具合」に見えて実は環境や並行作業が原因、というケースに定期的に当たる。ここで誤診すると、存在しないバグの修正に実装役を投入することになる。

## 1. テストの失敗が、環境起因かロジック不具合か

### 判定表

| 観測 | 環境起因（資源枯渇・フレーク） | ロジック不具合 |
|---|---|---|
| 落ちるテスト | 試行ごとに変わる | 毎回同じ |
| 失敗理由 | タイムアウト、接続失敗、リソース確保失敗 | アサーション不一致、例外 |
| 単独実行 | 通る | 落ちる |
| 変更との関係 | 触っていない領域も落ちる | 触った領域だけ落ちる |

### 手順

```bash
# 1. 失敗理由を全部読む（件数だけ見て判断しない）
#    すべて timed out か、アサーション不一致が混ざっているか

# 2. もう一度走らせ、落ちるテストが同じか確認する
#    8 件 → 1 件 → 別の 1 件、のように変わるならフレークの疑いが濃い

# 3. 落ちたテストだけを単独実行する
#    通れば、テスト自体は健全

# 4. マシンの状態を見る
uptime          # load average を CPU コア数と比較する
docker ps       # 動いているコンテナの数
nproc 2>/dev/null || sysctl -n hw.ncpu   # CPU コア数
```

load average が CPU コア数を大きく超えていれば（例: 10 コアで 39.7）、資源枯渇と確定してよい。

**なぜこの順番か**: 1〜3 はコード側の情報だけで進み、4 で初めて外部要因を持ち出す。逆順にすると「マシンが重いから」で調査を打ち切ってしまい、本物のバグを見落とす。安易に「テストが壊れている」とも「自分の変更のせい」とも言わず、観測を積み上げてから結論する。

環境起因と確定したら、それはユーザーへの判断案件になる（テストゲートをスキップするか、負荷が下がるまで待つか）。質問の型で返す。

## 2. 同じチェックアウトを別のエージェントが使っている

複数の Claude セッションやエージェントが同じディレクトリで並行作業していると、以下が起きる。

### 症状

- 自分が切ったブランチから、別のブランチに勝手に切り替わっている
- 自分がステージしたファイルが、相手のブランチにステージされたまま残っている
  - git のインデックスは**ブランチではなくリポジトリに紐づく**ため、ブランチを切り替えてもステージ内容は持ち越される
- hook が「コメントを 6 行追加した」と警告するが、自分の diff にはコメントが 1 行も無い
  - hook が作業ツリー全体を見ており、相手が書いたファイルを数えている

### 確認

```bash
git branch --show-current   # 自分が切ったブランチのままか
git status                  # 身に覚えのないステージ / 変更が無いか
git worktree list           # 他に誰かが作った worktree が無いか
```

### 対応

1. **まず自分の変更を unstage して元に戻す** — 相手のブランチや PR に混入させないため。混入してからの分離は、相手の作業も巻き込むので格段に難しくなる
2. 専用の worktree を切り直し、そこで作業をやり直す

**原則**: hook やツールが「自分の変更と辻褄の合わない」ことを言い出したら、ツールの誤作動を疑う前に作業ツリーの実際の状態を確認する。ツールは作業ツリー全体を見ているのに対し、自分は自分の変更しか見ていない。食い違いの原因はたいてい、その視野の差にある。

## 3. 無関係な変更を巻き込んでいないか

セッション開始時点で既に変更されていたファイルは、最後まで一度もステージしない。

```bash
# セッション開始時に記録しておく
git status --porcelain > /tmp/initial-dirty.txt

# commit 後に、意図したファイルだけか機械で確認する
git show --stat --oneline HEAD
gh pr view --json files --jq '.files[].path'
```

**なぜ機械で確認するか**: 目視は「見たはずのもの」を見落とす。特に `git add -A` や `git commit -a` を使った直後は、意図しないファイルが入っていても差分の見た目は自然になる。PR に無関係なファイルが 1 つ混ざるだけで、レビュワーは「この変更は何？」の確認に時間を取られ、レビューの質が落ちる。
