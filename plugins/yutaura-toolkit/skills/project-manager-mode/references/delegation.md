# サブエージェントへの委譲

調査役と実装役でプロンプトの設計が違う。両者を混ぜると、探索の途中経過が実装に混ざる / 調査結果に未検証の変更が紛れる、という形で品質が落ちる。

## 調査役（読み取り専用・本体ディレクトリ）

worktree は切らない。ファイルを書き換えないので隔離が要らず、切ると空の worktree が残るだけになる。

読み取り専用のエージェント種別が使えるならそれを選ぶ。無ければプロンプトで明示的に禁止する（「ファイルを一切変更しないこと」）。

### テンプレート

```
【問い】
<一文で。「〜は正しく動いているか」ではなく「〜が起きる条件は何か」のように、答えの形が決まる問いにする>

【調べる範囲】
<ディレクトリ・ファイル・機能の範囲。広すぎると結論が薄まる>

【返してほしい形式】
- 結論（3 行以内）
- 根拠（file:line 形式で。該当箇所の引用は必要最小限）
- 確認できなかったこと

【制約】
ファイルの変更・コマンドによる書き込みは行わない。読み取りと検索のみ。
```

**なぜ「返してほしい形式」を指定するか**: 指定しないと、調査役はファイルの中身を大量に持ち帰る。PM 側のコンテキストが調査対象のコードで埋まると、複数のフィードバックを並行して捌けなくなる。PM が必要としているのは「結論と、それを信じてよい根拠」だけ。

**なぜ「確認できなかったこと」を書かせるか**: 調査役は聞かれた問いに何らかの答えを出そうとする。空白を明示させないと、確信度の低い推測が結論と同じ調子で返ってくる。

## 実装役（書き込み可・専用 worktree）

**何を作るかが確定してから**渡す。「調べて直して」と丸投げすると、調査役の役目と混ざり、実装しながら方針が変わって差分が膨らむ。

### worktree の切り方

手段はホストによって異なる。使えるものを実測で確認してから選ぶ:

- Agent tool に隔離オプション（`isolation: "worktree"` 等）があればそれ
- 専用の worktree 作成ツールがあればそれ
- どちらも無ければ `git worktree add`

```bash
git worktree add ../<repo>-<topic> -b <branch-name> <base>
```

`<base>` は明示する。省略すると現在の HEAD が起点になるが、PM モードでは本体ディレクトリのブランチが他のエージェントによって切り替わっている可能性があるため、起点が意図しないものになりうる。

### テンプレート

```
【作業ディレクトリ】
<worktree の絶対パス。ここから出ないこと>

【変更内容】
<確定済みの変更。「〜を検討して」ではなく「〜を〜に変える」>

【守る規約】
<リポジトリのルール文書から抽出した、この変更に関係する規約>
<例: バージョン bump が要る / 対応する文書の更新が要る / コメントの書き方>

【検証】
<実行するコマンドと、通過条件>

【返してほしい形式】
- 変更したファイルの一覧
- 実行した検証とその結果
- 実行できなかった検証と、その理由
```

**なぜ「実行できなかった検証」を返させるか**: PM 自身の報告の型（4 番目の項目）がここに依存している。実装役が黙って省略すると、PM はそれを「実行された」と誤って報告する。報告の正確さは、委譲の各段でこの項目を引き継ぐことで保たれる。

## 並行して複数のフィードバックを捌くとき

調査役は並列に起動してよい（読み取りのみなので互いに干渉しない）。実装役はそれぞれ別の worktree を割り当てる。同じ worktree に複数を入れると、git のインデックスがリポジトリ単位で共有されるため、片方のステージ内容がもう片方に混ざる。

worktree が増えてきたら、作業完了後に片付ける（`git worktree remove`）。ただし削除は破壊的操作なので、中身のある worktree はユーザーに確認してから。
