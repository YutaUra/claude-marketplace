# wireframe

ローファイ・ワイヤーフレームは**構造を決める道具**であり、見た目を決める道具ではない。
答える問いは 3 つだけ: **何が画面にあるか / それぞれどこにあるか / 何が一番重要か**。
4 つ目の「どう見えるか」にはわざと答えない。見た目が整ったものを見せると、レビューする人は配置ではなくフォントや色の話を始めるからだ。

## 手順

### 1. 決めたい問いを特定し、成果物の種類を選ぶ

作り始める前に、会話・依頼文・リポジトリ内の既存画面や用語を読み、次を書き出す（ユーザーに見せる必要はない）:

- 誰が、どの仕事を片付けるための画面か
- 対象は 1 画面か、ひと続きのフローか
- 画面に載せなければならない情報と操作
- このワイヤーフレームで決着させたい構造上の問い

問いによって成果物を変える。**問いに答えられる一番安いものを選ぶ**:

| 決めたい問い | 成果物 |
| --- | --- |
| フローの手順・順番（どの画面が要るか、どこから何へ行けるか） | **breadboard**: 場所・操作・つながりを言葉で書く（レイアウトはまだ描かない） |
| どの仕組みで解くか（例: 絞り込みはタブか、チップか、サイドパネルか） | **thumbnail ボード**: 仕組みの違う小さな案を 3 案以上並べる |
| この画面に必要なものが揃い、正しく重み付けされているか | **1 画面のワイヤーフレーム**（PC / モバイル） |
| 複数画面が 1 つのタスクとしてつながるか（エラー・空状態の分岐を含む） | **wireflow**: ワイヤーフレームを、遷移を起こす操作から伸ばした矢印でつなぐ |
| 見た目は良いか | この skill の担当外（ハイファイ） |

- **必要以上に作り込まない**。仕組みが決まっていないのに 1 画面を作り込むのは早すぎ、画面構造が決まっていないのにクリックで遷移する版を作るのも早すぎる。
- 依頼が曖昧なら、聞く質問は 1 つまでにする。答えが無くても最も可能性の高い前提で進め、置いた前提を返答に書く。

### 2. デバイスを決める

PC 向けかモバイル向けか（両方か）で、キャンバス・ナビゲーション・主要操作の置き場所が変わる。
**必ず `references/devices.md` を読んでから描く**。両方必要なときは、モバイルから描いてから幅を広げる。

### 3. 出力形式を決め、対応する reference を読む

| 出力形式 | 選ぶ場面 | 読む reference |
| --- | --- | --- |
| **HTML（既定）** | 指定が無いとき。ブラウザで開いて比べる・クリックして確かめる | `references/output-html.md` |
| **Storybook** | 「Storybook で」と言われたとき。対象リポジトリに Storybook があり、そこで並べて見たいとき | `references/output-storybook.md` |
| **ASCII** | 「ASCII で」「テキストで」と言われたとき。チャット・issue・PR 本文・Markdown にそのまま貼りたいとき。breadboard や thumbnail ボードを手早く出したいとき | `references/output-ascii.md` |
| **SVG** | 「SVG で」と言われたとき。画像として資料・ドキュメントに貼りたい、ファイル単位で差分管理したいとき | `references/output-svg.md` |

形式が変わっても、下の「共通の見た目のルール」と「中身の作法」は変わらない。

### 4. 中身を作る

**`references/structure-and-annotation.md` を読んでから作る**（ゾーニング・レイアウトパターン・状態・注釈の詳細）。要点:

1. **ゾーンから決める**: 要素を置く前に、画面を「役割が 1 つずつあるゾーン」（全体ナビ / 現在地 / 主コンテンツ / 操作 / システム状態など）に分けて名前を付ける。名前の付かないゾーン（「その他」）はまだ存在理由が無い。
2. **優先度は大きさと位置だけで表す**: 大きさは 3 段階まで、「大」は 1 画面に 2 つまで。最重要のものと主要操作は、視線が最初に落ちる場所（PC は左上〜F 字の走査線上、モバイルは親指の届く下側中央）に置く。色に頼らないと伝わらない優先度は、まだ成立していない。
3. **本物のラベルと現実的な中身を使う**: lorem ipsum や「テキスト」「ボタン」は使わない。文言の長さ・件数・空状態によってレイアウトは変わるからだ。中身が未確定なら、もっともらしい正直な仮の文言を書き、後で直すべき点は返答に書く。
   - 例外: thumbnail ボードで本文段落の長さが問いに関係しないときに限り、段落を灰色のバーで代用してよい。見出し・ボタン・ラベルは代用しない。
4. **状態を落とさない**: データを扱う画面は、空・読み込み中・エラー・件数が多すぎる場合のうち、構造が変わるものを別フレームか注釈で示す。

### 5. 構造の違う案を出す（決め打ちされていない限り）

レイアウトが決まっていないなら、**構造の違う案を 2〜3 個**出す。違いを出す軸は、ナビゲーションの方式、情報のまとめ方と順番、主要操作の位置、情報の密度、一覧で見せるか段階的に進ませるか、などだ。

- 色を変えただけ・カードを入れ替えただけのものは別案と呼ばない。
- 各案に短い名前と、トレードオフを 1 文で付ける。推奨案を 1 つだけ示し、他の案も実際に採用できるものにする（負けるためだけの案を作らない）。
- 全案に共通する画面は、各案に繰り返さず 1 回だけ描く。
- ユーザーが構造を決めているなら、その案だけを作る。

### 6. 注釈を付ける

ワイヤーフレームは「何が」を示し、注釈は「なぜ」を運ぶ。

- 番号付きのマーカーを要素の横（文字や操作の上に重ねない）に置き、番号と 1 行の説明を対応させる。番号は画面ごとに 1 から振り直す。
- 書くのは**判断と問い**だけ: なぜここに置いたか、条件で変わる表示、業務ロジック、定石から外れた部分、空・エラー時の振る舞い、主要操作の結果、未解決の問い（「法務的に注記はファーストビューに要る？」）。
- 「これは検索ボックスです」のような、見れば分かることは書かない。注釈が多すぎると、大事な 3 つが 20 個に埋もれる。

### 7. 確かめてから返す

- **ぼかしテスト**: 細部を見ずに（目を細めて／5〜10px ぼかしたつもりで）見たとき、最初に目に入るものが意図した優先度と一致するか。画像プレースホルダーが主要操作より目立っていたら、配置か大きさを直す。
- **ローファイを保てているか**: 色が付いた部分が「主要操作・選択状態」「エラー」「注釈」だけになっているか。
- 出力形式ごとの確認項目（各 reference の末尾）を実施する。

返答には次を含める:

1. 成果物のパス（絶対パス）。ASCII ならその本文
2. 案があるなら、各案の名前・トレードオフ・推奨案
3. 番号付き注釈の一覧（形式が画像でもテキストで読めるように）
4. 置いた前提（デバイス、ログイン状態、データの有無など）と未解決の問い
5. **意図的に決めずに残したこと**（色・タイポグラフィ・最終文言など、ハイファイ段階で決めること）

## 共通の見た目のルール（全形式共通）

| 項目 | ルール |
| --- | --- |
| 色 | グレースケールのみ。背景 `#ffffff` / 面 `#f4f4f6` / 線 `#c9c9d1` / 補助文字 `#62626b` / 本文 `#26262e` |
| アクセント | 1 色（`#4338ca`）を**主要操作と選択状態だけ**に使う |
| エラー | `#b42318` を入力エラー・破壊的操作だけに使う。色だけでなくアイコンか文言でも示す |
| 注釈色 | アクセント・エラーと区別できる 1 色（`#d33` の破線や番号マーカー）。UI 要素には使わない |
| 書体 | システムフォント 1 種類（`system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP", sans-serif`）。優先度は大きさと太さで表し、書体では表さない |
| 文字サイズ | 12（注記）/ 14（本文）/ 18（見出し）/ 24（画面タイトル）の 4 段階だけ |
| 間隔 | 8px グリッド（細かい調整は 4px） |
| 装飾 | 影・グラデーション・角丸の多用・イラスト・写真は使わない。画像は「何の画像か」のラベル付きの灰色の箱で示す |

ワイヤーフレームは「意図的に未完成」にするが、雑にはしない。間隔のばらつき・読めない文字・崩れたレイアウトは、未完成ではなく単に壊れている。

## 置き場所

- 既定では**対象リポジトリの外**（セッションの scratchpad など）に作る。ワイヤーフレームは使い捨ての検討資料なので、頼まれない限りリポジトリに commit しない。
- Storybook 形式はリポジトリ内に置くことになるので、置き場所（ディレクトリ名・story のタイトル階層）を先に決め、返答で明示する。
- ユーザーが保存先を指定したらそれに従う。

## やらないこと

- ブランドカラー・最終タイポグラフィ・本番品質のコンポーネントを決める（ハイファイの担当）
- 本番コードとしてそのまま使える UI を書く（ワイヤーフレームのコードは捨てる前提）
- 複雑な状態管理・API 呼び出しの再現・凝ったアニメーション（クリックで画面が切り替わる程度まで）
- 依頼に無い機能を、画面の余白を埋めるために付け足す
