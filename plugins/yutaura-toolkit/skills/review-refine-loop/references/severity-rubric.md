# severity 分類と妥当性検証の基準

## 1. MUST / WANT / NIT の判定

分類は「指摘の内容」ではなく **「放置したときに何が起きるか」** で決める。同じ指摘でも成果物の目的が変われば severity は変わる。

| severity | 判定基準 | 典型例 |
| --- | --- | --- |
| **MUST** | 放置すると成果物が**目的を達成できない**。誤動作する、読み手を誤解させる、安全性を損なう、仕様と矛盾する | 条件分岐の抜けでループが終了しない / 手順が実行不能 / 事実と異なる記述 / 認可チェック漏れ |
| **WANT** | 直せば**明確に良くなる**が、無くても成果物は成立する。改善の方向が一意に定まる | 重複した説明の統合 / 判断基準が暗黙のまま / エラー時の挙動が未定義（ただし起きにくい） |
| **NIT** | 好み・表記ゆれ・些末な改善。**直さなくても誰も困らない** | 用語の揺れ / 節の順序 / 言い回し |

### 迷ったときの切り分け

- **MUST か WANT か迷う** → 「この成果物を初めて使う人が、この問題で詰まるか？」詰まるなら MUST
- **WANT か NIT か迷う** → 「直す前と後で、成果物の**挙動や判断**が変わるか？」変わらないなら NIT
- 「あったほうが親切」は WANT ではなく NIT のことが多い。**無いと判断を誤る**なら WANT

### severity を上げる条件

複数の lens が独立に同じ箇所を指摘した場合、統合して **1 段階上げる**。異なる観点から同時に見える問題は、単独観点からの指摘より実在する確率が高い。この昇格は同一指摘につき 1 回までとし、持ち越し指摘を次ラウンドの集約に再投入しただけでは再昇格しない（新たな裏付けが無いまま severity が膨張するのを防ぐため）。

## 2. 妥当性検証の 3 問

検証役は指摘を**信用しない**。対象を自分で読み直し、以下に答える。

### Q1: 妥当か（事実として成立しているか）

指摘された問題が**実際に対象に存在する**か。次の誤りが典型:

- **読み違い**: 指摘者が別の箇所と混同している
- **対処済み**: 指摘された懸念が、別の場所で既に手当されている
- **前提の誤り**: 指摘が成り立つ前提条件が、この成果物では成立しない
- **一般論の投影**: 「一般にこうすべき」を、文脈を見ずに当てはめている

**WANT / NIT で判断が割れたら「妥当でない」に倒す**。誤った指摘で成果物を変更するコストのほうが、その指摘を落とすコストより高い。

**MUST で判断が割れたら「妥当でない」ではなく保留（defer）に倒す**。棄却は以後の全ラウンドで再提出を遮断するので、「見送っても次ラウンドで再度出てくる」は成り立たない。検証役は発散役より弱い tier であり、一度の誤判定で正しい MUST 指摘が永久に失われ、重大な欠陥を残したまま「収束」と報告されてしまう。保留なら遮断されるのは選抜だけで、最終報告に残りユーザーが覆せる。

### Q2: 本質的か

直すと**成果物の目的達成に効く**か。次は本質的ではない:

- 表面的な整形・言い換えで、読み手の理解や挙動が変わらない
- 起こりうるが、起きたときの影響が軽微
- 「網羅性のため」に足す記述で、実際の判断には使われない

**本質的かどうかは severity とは独立**。MUST に分類された指摘が検証で非本質的と判明することもある（分類は発散側の主観なので当然起こる）。

### Q3: 修正は容易か

| 容易 | 困難 |
| --- | --- |
| 局所的な書き換えで完結する | 構造変更・全体の再編が要る |
| 修正方針が一意に決まる | 複数の選択肢があり、どれを取るか判断が要る |
| 他の箇所に波及しない | 他の記述・コードとの整合を取り直す必要がある |

## 3. 採否の決定

```
妥当 かつ (本質的 または 容易)  → 修正する
妥当 かつ 非本質的 かつ 困難    → 保留（最終報告で提示）
妥当でない                      → 棄却（次ラウンドのレビューに通知）

例外 1: ラウンド 2 以降の NIT は、妥当かつ容易でも保留に回す
例外 2: MUST の妥当性が割れた場合は、棄却ではなく保留に回す
```

この式の意図は **「価値が高いものは苦労してでも直す / 価値が低くてもタダなら直す」**。価値が低くて高コストなものだけを落とす。

### 例外 1: ラウンド 2 以降の NIT を直さない理由

素の式では「非本質的でも容易なら必ず修正」になる。言い回し・表記レベルの NIT は LLM レビュアーがほぼ無限に生成でき、しかも**直すと文面が変わって次ラウンドの新しい NIT の供給源になる**。結果、検証を通過した指摘が 0 件のラウンドが訪れず、実際の終了条件が常に「上限ラウンド到達」になる。毎ラウンド最上位モデルで全 lens を回しながら、成果物は整形 churn を続ける — コスト爆発と品質劣化が同時に起きる。

NIT をラウンド 1 に限定すると、初回に見つかった些末な改善は拾いつつ、ループの単調性（処理すべき指摘が減り続ける）が保たれる。

### 例外 2: MUST の誤棄却を防ぐ理由

Q1 の末尾を参照。棄却の遮断は恒久的で、検証役は発散役より弱い tier だという非対称性がある。

### 保留と棄却を区別する理由

- **保留**は「妥当な指摘だが、今は直さない」。ユーザーが見て「やっぱり直したい」と言える形で残す
- **棄却**は「指摘自体が誤り」。次ラウンドのレビュー役に伝えて再提出を防ぐ必要がある

両者を混ぜると、保留した妥当な指摘がレビュー役に「棄却済み」と伝わり、二度と出てこなくなる。

### 保留リストの扱い: レビュー役には渡さず、集約では落とす

保留は「レビュー役に黙っておく」が、**集約（Step 2）では棄却と同じように選抜から落とす**。この非対称が必要な理由:

- レビュー役に渡すと「もう出すな」と受け取られ、後でユーザーが「やっぱり直したい」と言ったときに情報が失われる
- 集約で落とさないと、保留済みの指摘が毎ラウンド再提出され、同じカテゴリの「1 件」枠を占有し続ける。他の妥当な指摘が一度も検証されないまま、「検証を通過した指摘が 0 件＝収束」と誤判定される

つまり保留指摘は毎ラウンド提出されるが、検証には進まない。無駄に見えるがコストはレビュー 1 件分の出力だけで、収束性と情報保持の両方が保てる。

## 4. 検証役の出力形式

```
verdict:   valid | invalid
essential: true | false        # verdict=valid のときのみ
effort:    easy | hard         # verdict=valid のときのみ
decision:  fix | defer | reject
reason:    判断の根拠（対象のどこを見てそう判断したか）
```

`reason` には **対象の具体的な箇所への参照**を含める。「一般にそうだから」で済ませた検証は、レビュー役の主張をなぞっているだけで裏取りになっていない。
