# レビュー観点（lens）の選び方

## 選定の原則

- **3〜6 個**。少ないと見落とす、多いと同じ指摘が別名で重複して検証コストが無駄になる
- **互いに重ならない**ように選ぶ。「正確性」と「事実確認」のような言い換えペアは片方に統合する
- **成果物の目的に効く順**に選ぶ。汎用の観点を機械的に全部当てない
- 各 lens には「**何を見ないか**」も書く。境界を明示しないと全 lens が全体を見て重複する

## 全成果物に共通する基礎 lens

対象の種類が何であれ、この 2 つはほぼ常に有効。

| lens | 見るもの | 見ないもの |
| --- | --- | --- |
| **目的整合** | この成果物が達成すべきことに対して、記述・実装が過不足ないか。目的に寄与しない要素はないか | 細部の正確性 |
| **悲観的検証（Devil's Advocate）** | 「この成果物は失敗する」という前提で、どこから崩れるかを探す。最も弱い仮定は何か | 改善提案（崩れる箇所の指摘に徹する） |

## 対象種別ごとの lens セット

### コード変更（diff / PR / ブランチ）

**専用の agent 群があるのでそれを使う**。`webapp-review` skill のルーティング表に従って、diff に関係する観点だけを選ぶ（`security-reviewer` / `authz-reviewer` / `db-design-reviewer` / `concurrency-reviewer` / `performance-reviewer` など）。

自前で lens を組むのは、それらの専門 agent でカバーされない領域（アルゴリズムの正しさ、API の使い勝手など）に限る。

#### severity の変換が必要

これらの agent は **Critical / High / Medium / Low の自由文**で返す。このループは MUST / WANT / NIT の構造化出力を前提にしているので、**集約側（オーケストレーター）が詰め直す**。agent 側のプロンプトを書き換えて形式を変えさせるより、受け取り側で変換するほうが agent を他の用途と共用できる。

| agent の severity | このループの severity |
| --- | --- |
| Critical / High | MUST |
| Medium | WANT |
| Low | NIT |

変換時に `location`（ファイル:行）と `problem` / `suggestion` を自由文から抽出する。抽出できない指摘は location を「不明」とせず、**該当箇所を自分で特定してから**集約に入れる（location が無いと修正役が別の箇所を直す）。

### skill / プロンプト / rules（Claude に読ませる文書）

| lens | 見るもの |
| --- | --- |
| **発火条件** | `description` でトリガーすべき場面に発火し、すべきでない場面に発火しないか。negative trigger が書かれているか |
| **実行可能性** | 手順が曖昧さなく実行できるか。「適切に」「必要に応じて」で判断を丸投げしていないか |
| **理由の明示** | 指示に「なぜそうするか」が添えられているか。理由のない命令は文脈が変わると誤適用される |
| **一貫性** | SKILL.md と references の記述が矛盾しないか。同じ概念に複数の名前が付いていないか |
| **既存資産との境界** | 既にある skill / agent と責務が重複していないか。連携すべきものを再実装していないか |

対象が skill そのものなら、`skill-creator` skill が持つ知見（progressive disclosure、description の書き方、トリガー精度の考え方）を lens の判断基準として参照できる。ただし skill-creator 本体のワークフロー（eval 実行・ベンチマーク）はこのループとは別路線なので、混ぜない。

### ドキュメント（README / 設計書 / 手順書）

| lens | 見るもの |
| --- | --- |
| **読み手視点** | 想定読者の前提知識で読み通せるか。前提が未説明のまま使われていないか |
| **事実正確性** | コマンド・パス・バージョン・挙動の記述が実際と一致するか（**実際に確認する**） |
| **抜け漏れ** | 手順の前提条件・失敗時の対処・後片付けが書かれているか |
| **保守性** | すぐ陳腐化する記述（バージョン番号・ファイル一覧）が、更新手順なしに埋め込まれていないか |

### 設計案・提案・ADR

| lens | 見るもの |
| --- | --- |
| **代替案の検討** | 採用しなかった選択肢とその理由が示されているか |
| **前提の脆さ** | 提案が依存している仮定のうち、崩れやすいものはどれか |
| **運用負荷** | 作った後に誰が面倒を見るか。継続コストが見積もられているか |
| **撤退可能性** | 間違っていたとき、どのくらいのコストで戻せるか |

### PR 本文 / コミットメッセージ

| lens | 見るもの |
| --- | --- |
| **Why の有無** | diff から読み取れない「なぜ」が書かれているか（What の繰り返しになっていないか） |
| **レビュアー視点** | レビュアーが最初に見るべき箇所・確認してほしい観点が示されているか |
| **検証の記述** | 何をどう確認したか。未確認の範囲が明示されているか |

## lens が見つからない場合

上記に当てはまらない成果物なら、「この成果物が**失敗するとしたら、その原因は何種類あるか**」を 3〜5 個挙げ、それぞれを lens にする。観点を先に決めるのではなく、失敗モードから逆算する。
