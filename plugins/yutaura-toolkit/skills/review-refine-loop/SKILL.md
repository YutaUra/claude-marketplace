# review-refine-loop: 収束するまで回す自己レビュー

成果物を多角レビューし、指摘の妥当性を検証し、採用したものだけ修正し、また最初からレビューする。これを妥当な指摘が尽きるまで繰り返す。

## このスキルが解く課題

自己レビューには構造的な failure mode が 4 つある。このループはそれぞれに対策を持つ。

| failure mode | 何が起きるか | 対策 |
| --- | --- | --- |
| **自己評価の甘さ** | 書いた本人が読むと、意図が補完されて欠陥が見えない | レビューを独立したエージェントに、複数観点で並列にやらせる |
| **指摘の洪水** | 出た指摘を全部直そうとして、本質的でない修正にコストが溶ける | 指摘を検証フェーズに通し、採否を明示的に判断する |
| **一発勝負** | 1 周直して終わり。修正が生んだ新しい問題が残る | 修正のたびにレビューをやり直す |
| **まとめ直しの干渉** | 複数の修正を同時に当てると、検証時の前提が崩れて何が効いたか分からない | 1 ラウンドで処理するのは各カテゴリ最大 1 件 |

## 設計原則

### 1. 発散・検証・修正を分離し、別のモデルに割り当てる

3 つのフェーズは要求される知性の種類が違う。同じモデルで通すと、最も難しいフェーズに合わせて全体が高コストになるか、最も簡単なフェーズに合わせて全体の質が落ちる。

| フェーズ | 要求される能力 | tier | 既定モデル |
| --- | --- | --- | --- |
| **発散（レビュー）** | 「誰も指摘していない問題に気づく」。探索空間が最も広く、ここでの見落としは下流で回復不能 | 最上位 | `fable` |
| **検証（妥当性判断）** | 与えられた 1 件の主張を、対象に当たって裏取りする。範囲は狭いが誤判定のコストが高い | 高推論 | `opus` |
| **修正（適用）** | 判断済みの指示を正確に反映する。判断は上流で済んでいる | バランス | `sonnet` |

**発散に最上位モデルを使うのが肝**。品質は上流で決まる。指摘されなかった問題は、どれだけ検証と修正を丁寧にやっても直らない。

モデル名は既定値であって固定ではない。ユーザー指定があればそれに従い、指定がなければこの tier の意図（発散＞検証＞修正の順に強いモデル）を保ったまま、その時点で利用可能な最上位モデルを割り当てる。

**検証役は発散役より弱い tier になる**。これは意図的なトレードオフだが、誤棄却のリスクを生む。そのため「MUST の棄却は defer に倒す」「棄却は必ず最終報告に出す」という安全弁を置いている（後述）。

### 2. 1 ラウンドで処理するのは各カテゴリ最大 1 件

MUST / WANT / NIT それぞれから 1 件ずつ、計最大 3 件だけを検証・修正の対象にする。理由は 2 つある。

- **修正の干渉を防ぐ**: 修正は成果物の状態を変える。同時に 10 件直すと、11 件目の指摘が「修正前の状態」に対するものになり、検証が陳腐化する。
- **カテゴリ間の飢餓を防ぐ**: severity 順に処理すると MUST が尽きるまで NIT に到達しない。逆に件数順だと NIT に時間が溶ける。カテゴリ横断で 1 件ずつ取ると、重いものを進めながら軽いものも消化される。

ただし **1 ラウンドあたりのエージェント起動コストが極端に高い状況**（モデルのレート制限に当たっている等）では、検証済みの指摘をまとめて適用してよい。その場合は修正を直列で当て、1 件ごとに対象を読み直して前提が崩れていないか確認する。制約の目的は「件数を 1 に保つこと」ではなく「検証の前提を壊さないこと」。

**残件が多いときは severity を絞る。** 上限到達で未検証が大量に残ったとき、次の実行は「MUST だけ」に絞ると、重いものから確実に消化できる。カテゴリを絞った実行では、対象外の severity は保留リストへ移して収束判定から外す（持ち越しに置いたままだと永久に検証されず、収束が成立しなくなる）。Workflow で回すなら `severityFocus: ['MUST']` と `picksPerCategory` で指定する。

### 3. 収束条件は「件数」ではなく「妥当な指摘が尽きたか」

「N 件直したら終わり」にすると、残っている重大な指摘を無視して終了する。逆に「指摘がゼロになるまで」にすると、レビューは何かしら書けてしまうので永遠に終わらない。

終了条件は **「MUST / WANT で検証を通過した指摘が 1 件も出なかったラウンドが発生したこと」**。

**NIT は収束判定に算入しない**。NIT（言い回し・表記）は LLM レビュアーがいくらでも生成でき、しかも直すと文面が変わって次の NIT の供給源になる。NIT を収束条件に含めると、成果物が整形 churn を続けたまま上限ラウンドまで回り続ける。

同じ理由で、**NIT を修正対象にするのはラウンド 1 だけ**にする。ラウンド 2 以降に出た NIT は妥当でも保留に回す。

**NIT のライフサイクル**: ラウンド 1・2 以降を問わず、その回の選抜で選ばれなかった NIT は次ラウンドへの持ち越しに入れず、集約（Step 2）の時点で保留リストへ移す。NIT は検証フェーズに到達する経路を持たないため、持ち越しに置いたままだと永久に未検証のまま滞留し、収束条件（Step 5）が成立しなくなる。

### 4. 「収束」は理想であって、通常の終わり方は上限到達

実測では、文書成果物（skill 一式）に 5 観点 × 3 ラウンドを回したとき、**未検証の指摘が 62 件積み上がった**（MUST 13 / WANT 35 / NIT 14）。レビュー役は毎ラウンド新しい指摘を生成できるのに対し、消化は各カテゴリ 1 件ずつなので、**供給が消化を上回る**。

これは設計の欠陥ではなく、LLM レビューの性質そのもの。だから:

- **収束を約束しない**。ユーザーに「妥当な指摘が尽きるまで回します」と言うと、際限ないコストを期待させる
- **上限ラウンドは予算**として扱う。開始前に「N ラウンド回してから残件を報告する」と合意する
- **未検証の残件は成果物の一部**として報告する。ユーザーが見て「この MUST は直したい」と選べる形にする

収束が現実的に起きるのは、対象が小さいか、観点を絞ったときだけ。

## ワークフロー

### Step 0: 対象・観点・復元点の確定

**何をレビューするか**を具体化する。「この skill」ではなく「`plugins/.../SKILL.md` と `references/*.md`」まで落とす。ファイル内容を各エージェントに貼るのではなく、**パスやコマンドを渡して自分で読ませる**（貼ると発散側が「渡された範囲がすべて」と誤認し、周辺の文脈を見に行かなくなる）。

**復元点を確保する。** このループは最大 `maxRounds × 3` 回、自律的にユーザーのファイルを書き換える。誤った修正や観点同士の振動で劣化したとき戻せる状態を先に作る:

```bash
git status --porcelain   # 未コミットの変更があるか確認
```

- クリーンなら、現在の HEAD が復元点になる。そのまま開始してよい
- 未コミットの変更があるなら、**ユーザーに commit か stash を促してから開始する**。ループの編集とユーザーの作業が混ざると分離できなくなる
- git 管理外の対象なら、対象をコピーして退避する

次に**レビュー観点（lens）**を 3〜6 個選ぶ。対象の種類ごとの観点セットは [references/review-lenses.md](references/review-lenses.md) を参照。

- **コード変更が対象**なら、観点を自前で作らず `webapp-review` の専門 agent 群（`security-reviewer` 等）に委譲できる。このスキルはその外側のループを担う。ただし **それらの agent は Critical/High/Medium/Low 形式で自由文を返す**ので、集約側で `Critical`/`High` → MUST、`Medium` → WANT、`Low` → NIT に変換し、このループの構造化形式に詰め直す必要がある
- 観点は**互いに重ならない**ように選ぶ。重なると同じ指摘が別名で複数回出て、検証コストが無駄になる

選んだ対象・観点・復元点をユーザーに提示してから開始する。

### Step 1: 多角レビュー（発散モデル・並列）

各 lens を 1 エージェントに割り当て、**同一ラウンド内では並列**に起動する。各エージェントは他の lens の指摘を見ない（見せると最初の指摘に引っ張られ、観点の独立性が失われる）。

各エージェントに渡すもの:

- 対象の読み方（パス / `git diff` コマンド）
- 担当 lens とその定義
- 成果物の**目的**（何を達成するための成果物か）。これがないと「一般論として良いこと」を指摘し始める
- **棄却済み指摘のリスト**（後述）。location と棄却理由を添え、「同趣旨の指摘も再提出しない」と明示する
- 出力は構造化（`severity` / `title` / `location` / `problem` / `suggestion`）

**レビューの失敗を収束と取り違えない。** エージェントは失敗することがある（レート制限・コンテキスト超過・権限）。失敗したエージェントの結果を黙って捨てると、指摘が 0 件になり「収束した」と誤判定する。起動した lens 数と返ってきた数を必ず突き合わせる:

- 1 つでも失敗したラウンドは、**そのラウンドで収束と判定しない**
- 半数以上が失敗したら、ループを止めて失敗理由をユーザーに報告する

これは机上の懸念ではない。この skill 自身の初回 self review で、検証エージェントが全滅した結果「収束しました」と報告される事故が実際に起きている。

### Step 2: 集約と MUST / WANT / NIT 分類

全 lens の指摘をマージする。

**重複の統合**: 同じ location・同じ趣旨の指摘を 1 件にまとめる。複数の lens が独立に同じ箇所を指摘したものは、単独観点からの指摘より実在する確度が高いので **severity を 1 段階上げる**（NIT→WANT→MUST）。統合せずに両方を処理すると、2 件目の修正役が「1 件目の修正で既に直った箇所」を別の形に書き直して壊す。**severity の昇格は同一指摘につき 1 回まで**。持ち越し指摘は次ラウンドの集約にも再投入されるが、その再統合では再昇格しない（新たな裏付けなしに毎ラウンド severity が膨張するのを防ぐため）。

**除外**: 以下は選抜前に落とす。

- **棄却リスト**に載っているもの（検証で誤りと判定済み）
- **保留リスト**に載っているもの（妥当だが直さないと判断済み）。これを落とさないと、粘着的な保留指摘が毎ラウンド同じカテゴリ枠を占有し、他の妥当な指摘が一度も検証されないまま「収束」と判定される

保留リストは**レビュー役には渡さず、集約側でだけ照合する**。レビュー役に渡すと「もう出すな」と受け取られ、後でユーザーが「やっぱり直したい」と言ったときに情報が失われる。

**分類**: 基準は [references/severity-rubric.md](references/severity-rubric.md) を参照。要約すると:

- **MUST**: 放置すると成果物が目的を達成できない / 誤動作する / 読み手を誤解させる
- **WANT**: 直せば明確に良くなるが、無くても成果物は成立する
- **NIT**: 好み・表記ゆれ・些末な改善

**持ち越し**: 選抜されなかった MUST / WANT の指摘は捨てずに次ラウンドへ持ち越す。LLM レビューは非決定的なので、「次も同じ問題を見つけてくれる」とは限らない。持ち越した指摘は次ラウンドの新規指摘とマージし、重複統合をかけ直す。**選抜されなかった NIT は持ち越さず保留リストへ移す**（設計原則 3 の NIT のライフサイクルを参照）。

### Step 3: 妥当性検証（検証モデル・カテゴリごとに 1 件）

各カテゴリから 1 件を選び、**独立したエージェントに検証させる**。検証役はレビュー役の主張を信用せず、対象を自分で読んで裏を取る。

**選定順位**（同カテゴリに複数あるとき）:

1. 複数の lens が独立に指摘したもの（Step 2 で severity を上げたもの）
2. 影響範囲が広いもの（中核手順に関わる / 複数箇所に波及する）
3. 同点なら先に出たもの

ラウンド 2 以降は NIT を選抜しない（設計原則 3 の理由による）。ラウンド 1 で選抜されなかった NIT も集約の時点で保留リストへ移っているため、そもそもラウンド 2 以降の候補には NIT が残らない。

検証で答えるのは 3 問（詳細は [references/severity-rubric.md](references/severity-rubric.md)）:

1. **妥当か** — 指摘された事実は本当に成立しているか。思い込み・読み違い・既に対処済みではないか
2. **本質的か** — 直すと成果物の目的達成に効くか。表面的な整形にすぎないか
3. **修正は容易か** — 局所的な変更で済むか、構造変更や新たな判断が要るか

採否は次で決まる:

| 判定 | 行き先 |
| --- | --- |
| 妥当 かつ（本質的 **または** 修正が容易） | **修正する**（ラウンド 2 以降の NIT を除く） |
| 妥当だが 非本質的 かつ 修正が困難 | **保留リスト**（最終報告で提示、直さない） |
| 妥当でない | **棄却リスト**（次ラウンド以降のレビューに「これは棄却済み」として渡す） |

**検証が失敗したときは、その指摘を捨てずに持ち越す。** エージェントが落ちたことと「検証した結果なにもなかった」ことは別物で、混同すると未検証の指摘が黙って消える。選抜した全件の検証が失敗したラウンドは、収束と判定してはならない（Step 1 と同じ理由）。

**MUST の妥当性が割れたときは棄却ではなく保留に倒す。** 棄却は以後の全ラウンドで再提出を遮断するため、検証役（発散役より弱い tier）が一度誤判定すると、正しい MUST 指摘が永久に失われたまま「収束」と報告される。保留なら遮断されるのは選抜だけで、最終報告には残りユーザーが覆せる。

### Step 4: 修正（修正モデル・直列）

採用された指摘を修正する。**並列にしない** — 同じファイルを触る可能性があり、競合すると壊れる。

修正役に渡すもの: 指摘の **location と title**、問題と修正方針、検証役の判断根拠、対象のパス、**「指摘された範囲だけ直す」という制約**（ついでの改善は次ラウンドのレビューに任せる。ここで広げると何が効いたか分からなくなる）。

修正が他の記述と矛盾を生む場合、その整合は取ってよいが、**整合のための変更は矛盾した箇所に限る**。「全体を見直す」は範囲外。

**修正役が「変更不要」と判断したものを、適用済みと混ぜない。** 修正役は対象を読んで「この指摘は既に対処済みだ」と結論することがある（レビュー役が古い状態を見ていた場合に起きる）。これを「適用した修正」として記録すると、直っていないものを直ったと報告することになる。変更したかどうかを明示的に返させ、別枠で集計する。変更していない以上、その location を修正済みとして数えてもいけない（振動検出が誤発火する）。

**修正が失敗したら「適用済み」として記録しない。** 直っていないものを直ったと報告することになるうえ、その location を修正済みとして数えると、次ラウンドの再指摘が振動と誤検出され、誤った理由でループが止まる。失敗した指摘は持ち越して次ラウンドで再処理する。

**リポジトリ規約に基づく付随作業は、ループの中でやらせない。** 修正役はリポジトリの規約ファイル（CLAUDE.md 等）を読むので、指示しないと「version を bump する」「README を更新する」といった作業を毎ラウンド繰り返す。これらは成果物の品質とは独立で、1 回やれば十分なものばかりなので、**ループ終了後にオーケストレーターがまとめて行う**。修正役へのプロンプトで明示的に範囲外と伝えておく。

### Step 5: 再レビューへ

Step 1 に戻る。終了条件:

- **収束**: MUST / WANT で検証を通過した指摘が 0 件で、**かつ MUST / WANT の未検証の持ち越しも残っていない**ラウンドが発生した（かつそのラウンドでレビューの失敗が無かった）。NIT はそもそも持ち越しに入らず保留リストへ移る（設計原則 3）ため、この判定には算入しない。「直すべきものが無かった」と「まだ検証していないものが残っている」は別物で、後者を収束に含めると、各カテゴリ 1 件制約で後回しになった指摘が一度も検証されないまま終わる
- **上限到達**: 既定 5 ラウンド。打ち切る場合は「未処理の指摘が残っている」と明示する
- **振動の検出**: 同じ location を 2 回以上修正した。**location は行番号でなく節単位（見出し/関数名などの安定識別子）で突き合わせる**。行番号は Fix のたびにずれるため、行番号ベースの一致では検出できない。これは観点同士が対立している兆候で、ループでは解けない。止めてユーザーに判断を仰ぐ。このとき採用済み・未適用の指摘（振動した指摘自身と、同ラウンドで採用された他カテゴリの指摘）は最終報告 6（未検証で残った指摘）に含める
- **レビューの大量失敗**: 半数以上の lens が失敗した（Step 1 参照）
- **検証の全件失敗**: そのラウンドで選抜した指摘の検証がすべて失敗した。収束ではないので、そう報告する

## Workflow tool での実行

このループは **条件分岐と可変回数のループを含む**ので、エージェントの裁量に任せるより決定的に書いたほうが安定する。Workflow tool 用のスクリプトテンプレートを [references/workflow-template.md](references/workflow-template.md) に置いてある。

Workflow tool が使えない場合（または対象が小さい場合）は、Agent tool を手で並列起動して同じ手順を踏めばよい。ループの形は変わらない。

**ユーザーが明示的に依頼していない限り、Workflow tool は使わない**（コストが大きいため）。手動での Agent 起動で代替できる。

## 最終報告

ループ終了時に以下を出す。修正内容の羅列だけで終わらせない。

1. **ラウンド数と終了理由**（収束 / 上限 / 振動 / レビュー失敗）。上限到達は失敗ではなく通常の終わり方（設計原則 4）
2. **適用した修正**: ラウンドごとに severity とタイトル。**実際にファイルが変わったものだけ**を数える
3. **変更不要と判断されたもの**: 修正役が「既に対処済み」と結論した指摘。これが多いときは、レビュー役が古い状態を見ているシグナル
4. **保留リスト**: 妥当だが直さなかったもの。「なぜ直さなかったか」を 1 行で
5. **棄却リスト**: 妥当でないと判断したもの。**判断理由付き**。検証役は発散役より弱い tier なので誤判定しうる。ユーザーが覆せる形で出す
6. **未検証で残った指摘**: 上限到達・振動・失敗で終わったとき、持ち越しキューに残っているもの
7. **検証役の独立性に問題がある場合はその旨**（成果物の著者自身が検証を兼ねたときなど）

## アンチパターン

- **レビュー役に成果物を貼り付ける**: 渡された範囲しか見なくなる。パスを渡して読ませる
- **レビュー役に「目的」を渡さない**: 一般論の指摘ばかりになり、その成果物にとって重要かどうかが判断できない
- **エージェントの失敗を収束と取り違える**: 起動数と返却数を突き合わせない実装は、全滅しても「指摘なし＝収束」と報告する
- **検証を省いて全部直す**: 指摘の中には誤りが混じる。検証なしで直すと成果物が劣化する
- **検証役にレビュー役と同じ情報しか渡さない**: 検証役は対象を自分で読み直さないと裏取りにならない
- **棄却リストを次ラウンドに渡さない**: 同じ誤指摘が毎ラウンド復活し、収束しない
- **保留リストを集約で落とさない**: 粘着的な保留指摘がカテゴリ枠を占有し、他の指摘が検証されないまま収束判定が出る
- **NIT を収束条件に含める**: 直すたびに新しい NIT が生まれ、整形 churn のまま上限まで回る
- **未検証の持ち越しを見ずに収束と判定する**: 「このラウンドで直すものが無かった」だけでは、後回しにした指摘が残っている
- **修正を並列で当てる**: ファイル競合で壊れる。直列で当てる
- **修正役に裁量を与えすぎる**: 「ついでに他も良くして」は、次ラウンドのレビュー対象を無駄に広げる
- **棄却した指摘を報告しない**: 検証役の誤判定をユーザーが検出できなくなる
- **修正役に付随作業までやらせる**: version bump や README 更新を毎ラウンド繰り返す。ループ外で 1 回やればいい
- **失敗した修正を「適用済み」に積む**: 偽の成功報告になり、振動検出も誤発火する
- **「変更不要だった」を適用済みに積む**: 同じく偽の成功報告。修正役は「既に対処済み」と判断することがある
- **復元点を作らずに始める**: 最大 15 回の自律編集を、戻せない状態で走らせることになる
- **収束を約束する**: レビューの供給は尽きない。上限ラウンドを予算として提示し、残件を渡すのが現実的な着地
- **小さな成果物に使う**: 1 ラウンドでも数エージェント起動する。typo 修正レベルには使わない

## 連携するスキル

- **webapp-review**: コード変更が対象のとき、Step 1 の lens として専門 reviewer agent 群をそのまま使える。webapp-review は「指摘を出して止まる」、この skill は「検証して直すまで回す」という役割分担。出力形式の変換は Step 0 を参照
- **code-review**（組み込み）: 単発のコードレビューと `--fix` による適用を担う。**1 周で足りるならこちらが軽い**。この skill を使うのは、収束までの複数周回が必要なとき
- **decision-council**: 振動を検出してループを止めたとき、対立する観点のどちらを取るかの判断に使える。ただし council も複数エージェントを起動する重い skill なので、**対立が後戻りコストの高い設計判断を伴う場合に限る**。言い回しレベルの対立なら、ユーザーに直接聞くほうが速い
- **comment-cleanup**: コード修正を伴うラウンドの後、commit 前の仕上げとして
