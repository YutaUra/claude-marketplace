# webapp-review: 専門レビュワーによる多角レビュー

Web アプリの変更 diff を分析し、関係する専門レビュワー agent だけを並列起動して、統合レポートを作る。

## 手順

### 1. レビュー対象の確定

引数や文脈から対象を決める。指定がなければ working tree の diff:

```bash
git diff HEAD          # 未コミットの変更
git diff main...HEAD   # ブランチ全体
gh pr diff <number>    # PR
```

diff が空なら対象をユーザーに確認する。

### 2. 観点の選定（ルーティング）

diff の内容から**関係する観点だけ**を選ぶ。全部起動するのは禁止（ノイズ・コスト・希釈された指摘になる）。選定基準:

| Agent | 起動条件（diff にこれが含まれるとき） |
| --- | --- |
| `db-design-reviewer` | スキーマ定義・マイグレーションファイル・モデルの関連定義 |
| `api-design-reviewer` | ルーティング・コントローラの入出力・OpenAPI/GraphQL スキーマ・シリアライザ |
| `authn-reviewer` | ログイン・セッション・トークン・パスワード・OAuth・MFA |
| `authz-reviewer` | ID を受け取ってリソースにアクセスするコード全般・権限/ロール・テナント。**迷ったら起動する**（認可バグは見逃しコストが最大） |
| `payment-reviewer` | 決済・課金・サブスク・ポイント/クーポン・金額計算 |
| `security-reviewer` | 外部入力処理・SQL/コマンド組み立て・HTML 出力・ファイルアップロード・外部リクエスト・依存追加 |
| `concurrency-reviewer` | 在庫/残高/予約など競合資源の更新・トランザクション・バックグラウンドジョブ・Webhook ハンドラ |
| `performance-reviewer` | クエリ・ループ内 I/O・一覧/集計・キャッシュ・大量データ処理 |
| `audit-trail-reviewer` | 金銭/権限/PII の更新パス・管理者操作・台帳/ポイント/残高テーブル・イベントソーシング構成 |
| `sre-reviewer` | エラーハンドリング・リトライ・タイムアウト・外部依存追加・設定変更・デプロイ手順に影響する変更 |
| `legal-reviewer` | PII の取得/送信・外部 SDK/解析ツール追加・購入/解約フロー・ポイント/前払い機能・メール配信・OSS 依存追加 |
| `marketing-reviewer` | 公開ページ・URL 変更・meta/OGP・計測タグ/イベント・フォーム/購入導線・メール文面 |

目安は 2〜6 agents。ユーザーが観点を指定した場合はそれに従う。選定結果と理由を 1 行ずつユーザーに示してから起動する。

### 3. 並列起動

選定した agent を **1 メッセージ内で並列に** Agent tool で起動する。各 agent への prompt には必ず含める:

- レビュー対象の取得方法（`git diff main...HEAD` 等の具体的なコマンド。diff 本文を貼るのではなく agent 自身に読ませる）
- リポジトリの文脈（フレームワーク、既知の前提があれば）
- 「あなたの専門観点のみに集中し、他観点への言及は不要」という指示
- 出力形式は各 agent の定義に従う

### 4. 統合レポート

全 agent の結果を待ち、以下の形式で統合する:

1. **サマリ**: 1〜3 文。マージ可否の temperature（問題なし / 軽微な指摘のみ / 要修正 / Critical あり）
2. **指摘一覧**: 全観点を混ぜて severity 順にソート。各指摘に `[観点名]` タグと `ファイル:行` を付ける
3. **重複の統合**: 複数 agent が同じ箇所を指摘した場合は 1 つにまとめ、観点タグを併記（複数観点からの指摘は重要度が高いシグナル）
4. **要法務確認**: legal-reviewer の「要法務確認」ラベル付き指摘は独立セクションに分ける（エンジニアが直せるものと混ぜない）

### 5. 修正するかの確認

レポート提示後、修正まで行うかはユーザーの指示を待つ（レビューと修正は別のタスク）。

## 注意

- agent が「指摘なし」を返すのは正常。無理に指摘を絞り出させない
- diff が巨大（数千行超）な場合は、agent ごとに担当ファイル群を絞って渡す
- このリポジトリ固有の慣習（CLAUDE.md・rules）と矛盾する指摘は統合時に落とすか、その旨を注記する
