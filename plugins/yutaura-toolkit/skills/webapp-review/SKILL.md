# webapp-review: 専門レビュワーによる多角レビュー

Web アプリの変更 diff を分析し、関係する専門レビュワー agent だけを並列起動して、統合レポートを作る。

## 手順

### 1. レビュー対象の確定

引数や文脈から対象を決める。指定がなければ working tree の diff:

```bash
git diff HEAD          # 未コミットの変更
git diff main...HEAD   # ブランチ全体
gh pr diff <number>    # PR
```

diff が空なら対象をユーザーに確認する。

### 2. 観点の選定（ルーティング）

diff の内容から**関係する観点だけ**を選ぶ。全部起動するのは禁止（ノイズ・コスト・希釈された指摘になる）。選定基準:

| Agent | 起動条件（diff にこれが含まれるとき） |
| --- | --- |
| `db-design-reviewer` | スキーマ定義・マイグレーションファイル・モデルの関連定義 |
| `api-design-reviewer` | ルーティング・コントローラの入出力・OpenAPI/GraphQL スキーマ・シリアライザ |
| `authn-reviewer` | ログイン・セッション・トークン・パスワード・OAuth・MFA |
| `authz-reviewer` | ID を受け取ってリソースにアクセスするコード全般・権限/ロール・テナント。**迷ったら起動する**（認可バグは見逃しコストが最大） |
| `payment-reviewer` | 決済・課金・サブスク・ポイント/クーポン・金額計算 |
| `security-reviewer` | 外部入力処理・SQL/コマンド/テンプレート組み立て・サーバ側 HTML 出力・ファイルアップロード/配信・外部リクエスト・XML/シリアライズ・CSRF 除外・プロキシ/Host ヘッダの利用・LLM / Agent・ツール呼び出し・キュー/イベントハンドラ |
| `client-security-reviewer` | フロントエンド JS/TS（DOM 操作・遷移・fetch 組み立て）・セキュリティヘッダ/CSP・CORS 設定・postMessage・WebSocket・Service Worker・フロントのビルド設定（公開 env・source map） |
| `supply-chain-reviewer` | package manifest / lock file・CI workflow・Dockerfile / compose / k8s manifest・パッケージ公開設定 |
| `concurrency-reviewer` | 在庫/残高/予約など競合資源の更新・トランザクション・バックグラウンドジョブ・Webhook ハンドラ |
| `performance-reviewer` | クエリ・ループ内 I/O・一覧/集計・キャッシュ・大量データ処理 |
| `audit-trail-reviewer` | 金銭/権限/PII の更新パス・管理者操作・台帳/ポイント/残高テーブル・イベントソーシング構成 |
| `sre-reviewer` | エラーハンドリング・リトライ・タイムアウト・外部依存追加・設定変更・デプロイ手順に影響する変更 |
| `legal-reviewer` | PII の取得/送信・外部 SDK/解析ツール追加・購入/解約フロー・ポイント/前払い機能・メール配信・OSS 依存追加 |
| `marketing-reviewer` | 公開ページ・URL 変更・meta/OGP・計測タグ/イベント・フォーム/購入導線・メール文面 |

目安は 2〜6 agents（security / client-security / supply-chain は diff が触れた層の分だけ起動する。サーバだけの diff で client-security を足すような「念のため」の起動はしない）。ユーザーが観点を指定した場合はそれに従う。選定結果と理由を 1 行ずつユーザーに示してから起動する。

### 3. 並列起動

選定した agent を **1 メッセージ内で並列に** Agent tool で起動する。各 agent への prompt には必ず含める:

- レビュー対象の取得方法（`git diff main...HEAD` 等の具体的なコマンド。diff 本文を貼るのではなく agent 自身に読ませる）
- リポジトリの文脈（フレームワーク、既知の前提があれば）
- 「あなたの専門観点のみに集中し、他観点への言及は不要」という指示
- 出力形式は各 agent の定義に従う。加えて、各指摘に次の 3 点を必ず書かせる:
  - **前提条件**: 攻撃や不具合に必要な権限（認証不要 / 一般利用者 / 管理者）とデータの状態。空欄にしない
  - **確度**: 確実（diff 上で成立を確認） / 要確認（diff の外の設定・別レイヤ次第）
  - **事実と推定の区別**: diff で確認した事実と、推定した影響を分けて書く。確認していない影響（全件漏えい等）を要約や severity に入れない
- diff に秘密情報（トークン・鍵・個人情報）が含まれていても、その値を出力に転記させない（項目名と場所だけ）

### 4. 統合レポート

全 agent の結果を待ち、以下の形式で統合する:

1. **サマリ**: 1〜3 文。マージ可否の temperature（問題なし / 軽微な指摘のみ / 要修正 / Critical あり）
2. **指摘一覧**: 全観点を混ぜて severity 順にソート。各指摘に `[観点名]` タグ・`ファイル:行`・確度を付ける
   - 見出しは脆弱性の分類名ではなく「誰が何をできてしまうか」の結果文にする（例:「未認証利用者が非公開プロフィールを取得できる」）。分類名（CWE / OWASP）は補足に回す
   - 修正案は「根本対策 / 追加対策（多層防御）」を分ける。特定の入力値を拒否するだけの案や CSP の追加だけで済ませる案を根本対策として扱わない
   - Low の指摘は詳細を書かない。末尾の「Low（軽微）」節に `[観点] ファイル:行 — 要約` の 1 行ずつで並べる（Critical〜Medium の判断材料を埋もれさせないため）
3. **重複の統合**: 複数 agent が同じ箇所を指摘した場合は 1 つにまとめ、観点タグを併記（複数観点からの指摘は重要度が高いシグナル）。同じ根本原因が複数箇所にある場合も 1 件にまとめ、該当箇所を列挙する（件数を水増ししない）
4. **要法務確認**: legal-reviewer の「要法務確認」ラベル付き指摘は独立セクションに分ける（エンジニアが直せるものと混ぜない）
5. **レビュー範囲**: 起動した観点と起動しなかった観点、巨大 diff で絞ったファイル、diff の外に依存して判断を保留した前提を末尾に書く。「指摘なし」は「その観点で問題が見つからなかった」であって「問題が存在しない」ではない

severity は脆弱性の種類ではなく攻撃条件で決める（ネットワーク越しに届くか、必要な権限、利用者の操作が要るか、影響を受ける範囲、データの重要度、既存の緩和策）。「CSP がない」「Server ヘッダが見える」のような単独の事実を、それだけで High 以上にしない。逆に、利用者の操作（リンクを踏む・ページを開く）が要る攻撃でも、ログイン済み利用者の権限で状態変更や情報取得が成立するなら、操作が要ることだけを理由に High から下げない（CSRF・postMessage・DOM XSS など）。

### 5. 修正するかの確認

レポート提示後、修正まで行うかはユーザーの指示を待つ（レビューと修正は別のタスク）。

## 注意

- agent が「指摘なし」を返すのは正常。無理に指摘を絞り出させない
- diff が巨大（数千行超）な場合は、agent ごとに担当ファイル群を絞って渡す
- このリポジトリ固有の慣習（CLAUDE.md・rules）と矛盾する指摘は統合時に落とすか、その旨を注記する
